CRM データを補完するときは、改善したい判断を決め、不足する項目を特定し、固定したサンプルで検証してから書き戻します。最初は契約済みのデータ提供元を使ってください。別の提供元や Clay のワークフローを追加するのは、追加費用に見合う具体的な不足がサンプルで確認できた場合です。

これは評価方法の提案であり、顧客の成果報告ではありません。製品ドキュメントの確認日は2026年11月1日です。以下のサンプル数、レビュー規則、計算は説明用の運用案です。ベンダーのベンチマークや売上増加の保証ではありません。

## 判断を1つ選びます

「CRM の全項目を埋める」は適切な目的ではありません。「事業を行う国に基づいてアカウントを正しい担当区域へ割り当てる」なら検証できます。製品を選ぶ前に、実行する処理、必須項目、誤答の影響を書き出してください。

企業ドメインと既存の CRM レコード ID をアカウントの基準にします。ドメインだけでは子会社、共通ブランド、買収を解決できません。曖昧な一致はレビューへ回し、言語モデルに黙って企業を選ばせないでください。連絡先では、メールアドレスを使用可能と判断する前に本人と現在の勤務先を確認します。

| 判断 | 最低限の根拠 | 却下またはレビューする条件 |
| --- | --- | --- |
| 担当区域への割り当て | 確認済みの企業識別と事業を行う国 | 登記住所と事業所在地が食い違う |
| ICP 適合判断 | 文書化した評価基準の属性と出典 | 必須属性が不明、または推測にすぎない |
| 連絡先の準備 | 現在の勤務先と独立して検証した連絡先項目 | 勤務先が古い、本人が曖昧、または検証がない |
| アカウント調査 | 出典 URL、関連する抜粋、確認日 | 抜粋が提案された記述を裏付けない |

当面の課題に必要な最小限の行を選んでください。企業単位の分類のために電話番号を購入する必要はありません。必須項目が空欄だからといって Claude に売上を創作させないでください。

## 段階的に補完します

最初に入力を正規化し、重複を除きます。元の値を別の列に保持し、`record_id`、`company_domain`、各行を処理する理由を保存してください。その判断について最新の承認済み値が既にあるレコードは除外します。

次に1つの提供元へ問い合わせます。返された値、提供元、確認日、利用できる根拠を保持します。「提供元が値を返した」と「レビュー担当者が値を承認した」は別の状態です。2つ目の提供元を使う意味があるのは、未解決の矛盾を増やさずに欠損または却下項目を解決できる場合です。

テーブル全体を再処理せず、未解決の行だけに代替の提供元を使います。[Clay の条件付き実行](https://university.clay.com/docs/conditional-runs)は項目値に応じて処理を実行できます。[Apollo の waterfall ドキュメント](https://www.apollo.io/product/waterfall)は複数提供元の照会を説明しています。どちらも対象セグメントでの正確性を証明する機能ではありません。それはサンプルのレビューで測定します。

最後に、提供した根拠からの抽出や分類に Claude を使います。事実の抽出と決定論的な採点基準を分けてください。もっともらしい説明は出典ではありません。出典にアクセスできない、または情報が足りない場合は不明のまま残し、人に回します。

[Clay と Claude のリード補完ワークフロー](/ja/workflows/lead-enrichment-clay-claude/)には、この分離を始めるための成果物があります。オフラインの例は合成データです。チェックの仕組みを理解した後、CRM 更新を接続する前に自社の実データで試してください。

## 100件で評価します

予定する処理対象から固定の100件を選び、実際に扱う地域、企業規模、データの古さを含めます。難しいレコードや不完全なレコードを除かないでください。有名企業だけの便利なリストでは、発見すべき失敗が隠れます。

入力、必須項目、日付、承認規則を固定します。基準となる提供元と候補ワークフローへ同じレコードを渡してください。可能な限り、返された各項目を独立した出典で確認します。判断できる参照先がなければ、正解ではなく未解決に分類します。

評価シートには次の列を用意します。

```text
record_id, segment, required_field, baseline_value, candidate_value,
provider, source_url, checked_at, reviewer_decision, rejection_reason,
credits_used, external_cost, review_minutes
```

API キーや不要な個人データをシートに入れないでください。出典へのアクセスと保存はチームの承認済み手順に合わせます。情報が食い違ったときにどの根拠を優先するか、責任者を決めてください。「最後の応答を採用する」は承認規則になりません。

| 指標 | 計算 | 確認すること |
| --- | --- | --- |
| カバレッジ | 返された必須項目数 / 要求した項目数 | 何らかの値が見つかったか |
| レビュー済み精度 | 承認された項目数 / レビューした返却項目数 | 返された値は使えたか |
| 承認行の割合 | 全必須チェックを通った行数 / 入力行数 | 何件を次へ進められるか |
| 承認行あたり費用 | 割り当てた実行費用 / 承認行数 | 有用な結果が費用に見合うか |
| レビュー負荷 | レビュー時間（分）/ 承認行数 | 手作業がどれだけ残るか |

不明と矛盾は別々に数えてください。カバレッジと精度は異なり、承認行の割合は営業の成約率ではありません。承認行が0件なら行あたり費用は定義できません。そこで展開を止めてください。

## 実行全体の費用を計算します

計算式は `run cost = allocated subscription cost + incremental usage + external API charges + review labor` です。契約に含まれるクレジットを追加使用料として重ねて計上しないでください。既存契約では、試験の追加費用と、契約費用を配賦した運用費用の両方を示します。

[Clay は Actions と Data Credits を分けて説明しています](https://university.clay.com/docs/actions-data-credits)。外部 API キーで不要になるのは対応する Data Credits であり、外部提供元の料金や Actions ではありません。[Apollo の使用量レポート](https://knowledge.apollo.io/hc/en-us/articles/9527776320781-Review-Credit-Usage-in-Apollo)では機能やリクエスト別に確認できます。月間費用を見積もる前に、実際の使用量を記録します。

以下は架空の例であり、Clay や Apollo の測定結果ではありません。入力100件から80行が承認され、配賦したプラットフォームとデータの費用は $24 です。レビューは30分、仮定した人件費は1時間 $40 とします。合計 $44、承認行あたり $0.55 です。代替提供元に $8 とレビュー15分を追加し、承認行が10行増えたとします。追加行あたりの限界費用は $18 / 10 = $1.80、全体では $62 / 90 = 約 $0.69 です。

追加された各行がその判断にとって $1.80 に見合う場合だけ、代替処理を承認してください。カバレッジの増加だけでは不十分です。例の全入力を、記録した費用、担当者の時給、承認結果に置き換えます。

## 購入、組み合わせ、現状維持を選びます

必要項目とエクスポートのチェックを通り、レビュー負荷が許容できるなら既製の補完機能を使います。提供元の順序、条件付き処理、根拠に基づく AI 分類を既存システムへ渡したい場合は Clay を検討してください。両方を購入する前に [Clay と Apollo の比較](/ja/vs/clay-vs-apollo/)を読んでください。

不足項目が行動を変えない場合や、レビューが手作業の調査より大変な場合は現状を維持します。独自スクリプトを作るのは、再試行、項目対応、アクセス管理、保守の責任者がいる場合です。その責任も費用の一部です。

初回の展開では、CRM への変更案をすべてレビューし、以前の値を残し、承認された項目だけを書き込みます。企業の取り違えや説明できない費用増加があれば停止してください。対象集団、提供元、プロンプト、評価基準が変わったらサンプルを再確認します。更新頻度は観測した項目の劣化と次の業務判断に合わせます。全項目を毎月更新するだけでは戦略になりません。
