A Model Context Protocol (MCP) server that exposes [Ashby](/en/tools/ashby/) as a tool surface to Claude — letting recruiting teams query the candidate database, read interview scorecards, surface pipeline status, and pull funnel analytics directly through prompts. Designed for recruiting teams that want their recruiters and hiring managers to interact with Ashby through Claude rather than the Ashby UI.

## What you'll need

- Claude Code or Claude.ai with MCP-enabled access
- [Ashby](/en/tools/ashby/) admin access plus API key with read scope (write scope optional, with caveats)
- Node.js 20+ for the MCP server runtime
- Server hosting (local for development, internal hosting for team use)
- Network access from the Claude environment to the Ashby API

## Setup

1. **Provision the API key.** In Ashby admin: create a service-account API key with read access to candidates, interviews, scorecards, and analytics. Document the scope; rotate per security policy.
2. **Clone and configure the MCP server.** The server exposes five tool surfaces:
   - `search_candidates(query)` — semantic search across the candidate database
   - `get_candidate(candidate_id)` — full candidate record with scorecards and interview history
   - `list_open_roles(filter)` — open roles by team, stage, time-open
   - `get_role_funnel(role_id)` — per-stage candidate counts and conversion rates
   - `get_interviewer_load(timeframe)` — per-interviewer interview count and load distribution
3. **Deploy the server.** Local for individual developer use; internal hosting (HTTPS, internal DNS) for team use. Include access logging.
4. **Wire to Claude.** Add the MCP server URL to Claude's MCP configuration. Verify connection with a test query.
5. **Test the five surfaces.** Search for a known candidate; pull their details; list active roles; check funnel for a specific role; check interviewer load. Verify outputs match the Ashby UI.

## Example interactions

Once configured, recruiters and hiring managers can ask Claude:

- "What's our offer-to-accept rate for senior engineering roles in the last 90 days?"
- "Pull the on-site debrief notes for [candidate] across all interviewers and surface the points of disagreement."
- "Show me all open requisitions in the platform engineering team that have been open more than 30 days, with their current funnel stage."
- "Which interviewers on the platform engineering team are over-loaded this week?"

Claude responds by issuing the appropriate MCP tool calls, retrieving the data, and synthesizing the answer.

## Security and access controls

Critical considerations:

- **Authentication.** Every Claude session authenticates as a specific user against the MCP server, which authenticates as that user against Ashby. No service-account-as-user.
- **Read vs write.** Default deployment is read-only. Write operations (advancing candidates, posting jobs, adding scorecards) require explicit additional authorization and audit logging.
- **Audit logging.** Every MCP tool call is logged with timestamp, user, query, and Ashby API call made. Critical for hiring-decision audit trail.
- **Scorecard data is sensitive.** Interview content includes evaluation that could be problematic if surfaced inappropriately; verify the access-control model matches what the team would do in the Ashby UI.
- **AI policy alignment.** Candidate and scorecard data is sensitive; verify [AI policy](/en/learn/ai-policy-for-legal-teams/) authorizes Claude access to recruiting data, particularly demographic-correlated content.

## Where it fits

This MCP server is for the recruiting team that has matured past the "we use Ashby because it's a good ATS" stage and into the "we want to operate Ashby data through AI workflows" stage. Compresses Ashby-UI time into Claude conversation time, with 2-5x throughput improvements on data-driven workflows ([funnel analysis](/en/workflows/hiring-funnel-anomaly-n8n/), [debrief synthesis](/en/workflows/interview-debrief-summary-skill/), [weekly digest](/en/workflows/weekly-recruiting-digest-skill/) generation).

## Watch-outs

- **Don't over-permission.** Read-only is the right default. Write operations through MCP create production-data risks not worth the convenience for most teams.
- **MCP servers expose data to Claude. Verify acceptable use.** Some Ashby data may be sensitive enough that exposing it via MCP requires legal/security review.
- **Performance considerations.** Large candidate-search queries can blow out token budgets. Tune the search tool to return summarized results with drill-down via subsequent MCP calls.
- **Don't bypass Ashby workflow.** MCP makes it easy to read; resist the temptation to also write candidate-stage changes directly. Stage changes should happen through Ashby UI with proper approval, not through Claude conversation.
- **Bias considerations.** AI-augmented candidate-data analysis can surface protected-class proxies. Audit the queries and responses periodically.
