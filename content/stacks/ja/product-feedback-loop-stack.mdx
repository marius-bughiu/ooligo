まず反論から始めます。それが正しい問いだからです。[Canny](/ja/tools/canny/) と [Productboard](/ja/tools/productboard/) は今や同じソースを読んでいます。Canny の Autopilot は Zendesk、Intercom、Slack、Gong、Help Scout、Freshdesk、Zoom、tl;dv からフィードバックを取り込み、さらに G2、Capterra、Trustpilot、App Store、Google Play の公開レビューも読みます。Productboard も Zendesk、Intercom、Slack、Gong、G2、App Store、Google Play を取り込みます。両方とも見つけたものを AI でクラスタリングし、両方とも重複排除します。両方を買うのは、同じ取り込みエンジンを二度買うように見えます。

重ならない部分こそが、このスタックが存在する理由です。Canny は顧客がログインし、投稿し、投票する board を運営し、要望が出荷されたときに投票者全員へ知らせる changelog を持ちます。Productboard の Portal はロードマップを公開しますが、これは配信面であって投票コミュニティではありません。引き換えに Productboard は優先順位付けの装置を握っています。目標に対するスコアリング、feature の定義、そして開発への引き渡しです。一方のツールは顧客が「何が重要か」を議論する場所であり、もう一方はプロダクトチームが決める場所です。どちらか一方しか必要ないなら、一方だけを買ってください。このページはあなた向けではありません。

その後者の半分は、2026年秋に高くなりました。Productboard は Free プランと Plus プランを廃止し、現在は Business と Enterprise のみを販売しています。どちらもデモ経由でしか契約できず、どちらも maker 5名の最低ラインがあります。スタック全体を安く試す方法はなくなり、それによってこのスタックが合う相手も変わりました。

## 各ツールの役割

**Zendesk** はボリュームの供給源であり、フィードバックシステムではありません。feature 要望の大半は、別件のサポートチケットの2段落目として届き、そこで消えていきます。このスタックにおける Zendesk の仕事は存在し続けることです。エージェントはチケットを解決するだけで、ワークフローを一切変えません。

**Canny** は顧客向けのレイヤーであり、重複排除のポイントです。Autopilot が Zendesk の会話を読み、要望を抽出し、既存の投稿があればそこに統合し、プロダクト領域に振り分けます。公開 board は要望が可視化され数えられる場所であり、changelog はループを閉じる手段です。

**Productboard** は社内のランキングレイヤーです。サポートと営業の会話を独自に取り込み、feature に紐づけ、目標に対してスコアを付け、確定した作業を Jira、Azure DevOps、GitHub、Trello、Shortcut へ送り出します。そのすべてにまたがる AI レイヤーである Spark は両プランに含まれ、クレジットで配分が制限されます。Productboard は公式の MCP サーバーも提供しているため、エージェントは UI の座席なしで feature やインサイトを照会できます。

**Slack** は、どちらのツールも開かない人たちにループを見せる場所です。Canny は新規投稿、コメント、投票の節目、ステータス変更を通知します。さらに Canny も Productboard も Slack を取り込み元として扱うため、`#customer-feedback` に書き込まれた要望が消えてしまうことはありません。

## 引き渡しの流れ

1. feature 要望を含むチケットが **Zendesk** に届きます → Canny の Autopilot が捕捉し、既存投稿と重複排除し、プロダクト領域へ振り分けます。
2. 要望が **Canny** の board に現れます → 他の顧客が投票し、投票の節目とステータス変更が **Slack** へ送られます。
3. 投稿が設定したしきい値に達します → **Jira または Linear** へ送られ、ステータスが双方向に同期されます。
4. **Productboard** が同じ Zendesk と Gong の会話を直接取り込み、feature に紐づけ、目標に対してランク付けします。
5. 作業が出荷されます → Jira または Linear のステータスが Canny の投稿へ同期して戻ります → **Canny の changelog** が投票した顧客全員に通知します。

ステップ4こそ、このスタックに穴がある箇所です。ここをごまかせば、ページの残りすべてが役に立たなくなります。**Canny と Productboard の間には、どちらの方向にもネイティブ連携が存在しません。** Canny の連携ディレクトリに Productboard は載っておらず、Productboard の連携ディレクトリにも Canny は載っていません。2026年11月9日に再確認済みです。

対策は、両者を直接つなごうとするのをやめ、issue tracker を共通の背骨にすることです。両ツールとも Jira とネイティブに同期し、どちらも同じ issue に紐づくため、Jira のキーが公開投稿と社内 feature をつなぐ結合点になります。この対策には2つの制約があります。1つ目は、Jira でなければならないことです。Canny は Linear とネイティブに同期しますが、Productboard が Linear に届くのは開発計画の同期機能ではなく、Spark の MCP コネクタ経由だけです。2つ目は、Productboard Business では Jira 連携が5接続までに制限されることです。Jira プロジェクトを多数抱える企業は、契約前にその対応関係を整理しておくべきです。他の選択肢はさらに悪いです。Zapier や Make のブリッジは以降あなたが所有し保守することになり、Canny の API を Productboard の API に突き合わせる方式は、3か月目には担当者のいない小さな社内連携になります。

## コストの基準線

2026年11月9日時点で確認。サポートエージェント8名と、ロードマップツールに書き込む必要のある4名のチームを想定します。

Productboard は価格を公開しなくなりました。同社が Business について最後に公開した定価は、年間契約で $59/maker/月 (月払いで $75) で、2026年9月付けの同社の請求に関する FAQ に記載されていました。これは見積もりではなく参考値として扱ってください。maker 5名の最低ラインがあるため、4名のチームでも maker 5名分を支払います。$295/月、つまり年間 $3,540 です。

節約型の構成: Zendesk Suite Team が年間契約で $55/エージェント/月 ($440)、Canny Pro が年払いで $79/月、Productboard Business が maker 5名の最低ライン ($295)。合計 $814/月、年間およそ $9,768 です。

より手厚い構成: Zendesk Suite Professional が年間契約で $115/エージェント/月 ($920) に、年払いで $50/エージェント/月の Copilot アドオン ($400) を加え、Canny Pro が $79、Productboard Business が $295。合計 $1,694/月、年間およそ $20,328 です。Copilot のエージェント支援機能は Professional ではアドオンであり、Suite Team では提供されていません。Zendesk の AI エージェントは座席単位ではなく自動解決 (automated resolution) 単位で課金されます。Suite Team にはエージェント1名あたり月5件、Professional には10件の解決が含まれ、追加の解決はコミット契約で $1.50、従量課金で $2.00 かかります。

フィードバック層は今や節約型の請求額の半分近く ($814 のうち $374)、手厚い構成ではおよそ5分の1を占めます。Plus が消える前の2026年8月には、どちらの構成でもおよそ4分の1でした。小規模なサポートチームにとって、今や交渉すべき項目は Productboard の最低ラインです。

この数字が保つかどうかは、2つの課金の仕組みで決まります。Canny はチームの座席数で課金しません。Free は tracked user 25名と manager 5名、Pro は tracked user 100名以上と manager 10名をカバーし、Business は 5,000名からです。ティアを押し上げるのは追跡するエンドユーザー数の増加であって、チームの増加ではありません。tracked user とはフィードバックに関連付けられた人すべてであり、Autopilot が見つけてきたユーザーも含まれます。Productboard は Spark のクレジットを計測します。Business には maker 1名あたり月 500 クレジットが含まれ、ワークスペース全体でプールされます。Enterprise には基礎クレジット 1,500 に加えて、追加 maker 1名ごとに 800 が含まれます。追加購入は、月払いプランでは 50 クレジットごとに $5、年間プランでは 600 クレジットごとに年 $60 です。maker 数を決める前に、デモ経由のトライアル中にクレジットの消費量を確認してください。

## バリエーション

**board を公開しないなら Canny を外す。** 顧客が要望を見ることも投票することもないなら、Canny の重ならない側の半分は消え、ロードマップ公開は Productboard の Portal が担えます。これで年間 $948 を節約でき、コネクタの継ぎ目もなくなります。判断基準は、ログインして投票する顧客を具体的に名指しできないなら、すでに持っている重複排除エンジンを買っているだけだ、ということです。

**ロードマップに書き込む人が5名未満なら Productboard を外す。** 最低ラインのせいで誰も使わない座席に支払うことになり、10名程度を下回るなら、優先順位付けはスコアリング用フィールドを持つ Jira か Linear に収まります。その場合は Canny と issue tracker だけでループ全体が回り、フィードバック層は $374 ではなく $79/月で済みます。

**Zendesk を Intercom か Pylon に替える。** Canny も Productboard も Intercom をネイティブに取り込むため、置き換えても引き渡しの流れはそのまま保たれます。

## このスタックが置き換えないもの

これは顧客が何を*したか*ではなく、何を*求めたか*しか教えてくれません。行動は [product adoption stack](/ja/stacks/product-adoption-stack/) の領域です。チケットの削減もしません。それは [AI support agent stack](/ja/stacks/ai-support-agent-stack/) の役割です。ディスカバリーの実践でもありません。投票数が測るのは、わざわざ投票する顧客の熱量であり、それはセグメントが保有する売上よりも、そのセグメントの声の大きさと相関します。CS のヘルスや更新管理のシステムでもありません。

対策とセットの注意点が2つあります。**両ツールが独立に Zendesk を取り込むと、同じチケット群について異なる2つのクラスタリングが生まれます。** PM と CS が同じ要望について異なる件数を同じ会議に持ち込んだ瞬間、どちらの数字も信用を失います。対策は、ソースごとに記録の正本を1つに定めることです。顧客から見えるものはすべて Canny が持ち、Productboard は営業コールと社内メモに向けます。**Productboard はまだピボットの途中です。** Hubert Palan は2026年4月15日に、同社が AI-only へ移行し、チームの30%超と別れると発表しました。さらに2026年9月の価格改定でセルフサーブのティアが廃止されました。対策は、生の verbatim をエクスポートできる Canny と Zendesk に保持し、Productboard は単独で所有していないコーパスの上に乗るランキング層として扱うことです。

## このスタックが正解になるとき

公開 board が実際に票を集めるだけの顧客数があり、要望がチケットに埋もれるほどサポート量が多く、ロードマップツールに実際に書き込む人が少なくとも5名いて、PM と CS のリードが共通のランク付きリストを持たないまま優先順位で対立していて、changelog を維持する担当者がいる。そのときに選んでください。

顧客数が少なく単に電話すれば済むとき — 30社のエンタープライズアカウントに投票 board を広げても、ノイズと偽の民意しか生みません — あるいはループの担当者が誰もいないときは見送ってください。要望を2年間「検討中」と表示し続ける公開 board は、最初から開かないより悪いです。それは、あなたが答えていないことの、恒久的でインデックスされ顧客から見える記録だからです。
