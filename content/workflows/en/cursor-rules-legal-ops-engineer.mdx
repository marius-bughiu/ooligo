A Cursor rules file (`.cursor/rules/legal-ops-engineer.md`) tuned for the in-house legal-tech engineering work patterns: building [CLM](/en/learn/contract-lifecycle-management/) configurations, writing [MCP servers](/en/workflows/mcp-server-ironclad-legal/) for legal AI tools, automating intake forms, and integrating legal-tech systems. Encodes the conventions and guardrails that distinguish legal-tech engineering from general application engineering.

## What you'll need

- Cursor (latest version with Project Rules support)
- Working Legal Ops engineering project — typically TypeScript or Python automation, integration code, or CLM configuration repos
- Familiarity with the legal-tech systems being integrated ([Ironclad](/en/tools/ironclad/), [Agiloft](/en/tools/agiloft/), e-billing system, MCP)

## Setup

1. **Create the rules directory.** In your project root: `.cursor/rules/`.
2. **Drop the rule file.** Save the following as `.cursor/rules/legal-ops-engineer.md`:

```markdown
# Legal Ops engineer conventions

## Audit trail is mandatory
Every read or write against legal data systems (CLM, e-billing, matter management) must produce an audit log entry with: timestamp, user identity, system accessed, action taken, data scope. Never write code that touches legal data without an explicit audit log call. If the audit infrastructure doesn't exist, build it before the integration.

## Privilege and confidentiality safety
Code that handles contract content, communications, or matter data requires explicit handling of privilege flags. Never:
- Cache privileged content beyond the request scope
- Send privileged content to non-Tier-A AI tools per the firm's AI policy
- Log privileged content content (log metadata only)

## Read-only by default
Integrations with legal data systems default to read-only. Write capabilities require explicit additional authorization, separate API keys with write scope, and a written rationale documenting why direct write through automation is needed vs system UI.

## Idempotency for retry safety
Every webhook handler, API endpoint, and automation step must be idempotent. Legal systems often retry on timeouts; non-idempotent code produces duplicate matters, duplicate invoices, duplicate workflows.

## Schema-driven, not string-driven
LEDES invoices, SIG questionnaires, contract metadata — all have schemas. Always parse to the schema, validate, then operate on structured data. Never regex-extract from raw text in production code.

## Test against staging legal systems
Production CLM, e-billing, and matter management systems contain real legal data. All integration testing happens against staging instances or sandboxes. Never test against production with real matter data.

## Security review for new integrations
Any new integration with a legal data system gets security review before production deployment. AI vendor integrations specifically require AI policy review per the firm's [AI policy](/en/learn/ai-policy-for-legal-teams/).

## Document the data flow
Each integration includes a data flow diagram showing: source system, data fields, transformation, destination system, retention policy. Lives in the repo `docs/` folder, updated when the integration changes.
```

3. **Commit the rules file.** Goes in version control with the rest of the project.
4. **Verify Cursor picks them up.** Cursor's Project Rules indicator should show the rules are active.

## What the rules do

When Cursor's AI is helping you write code in this project, the rules act as system-level instructions that shape the AI's suggestions:

- Suggests audit-log calls automatically when the AI sees you writing CLM API calls
- Refuses to suggest caching or logging that would violate privilege handling
- Flags non-idempotent webhook patterns
- Suggests schema validation when the AI sees raw-text parsing of structured legal data formats

The rules don't enforce behavior at runtime — they shape the AI assistant's suggestions during development.

## Where it fits

For Legal Ops teams that have a "Legal Ops engineer" role (or a Legal Ops Manager doing engineering work themselves), these rules ensure AI-assisted development produces code that matches legal-tech conventions, not generic application conventions.

For legal teams without dedicated engineering capacity, this is less directly useful — but worth installing in any vendor- or partner-developed legal-tech project to encourage compatible conventions.

## Watch-outs

- **Rules require Cursor Project Rules support.** Older Cursor versions don't support project-scoped rules; verify before deploying.
- **Don't over-specify.** Rules that cover every possible style choice produce over-restrictive AI suggestions. Focus on the rules that prevent material legal-data risk.
- **Update with practice.** The conventions evolve as the team's stack evolves. Review the rules quarterly; remove what's no longer relevant; add what's been learned.
- **Rules don't replace code review.** They shape suggestions; human code review on legal-data integrations remains required.
