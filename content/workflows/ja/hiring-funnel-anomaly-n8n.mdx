採用オペレーションで、どの求人や選考段階を詳しく調べるべきか知りたい場合に使うワークフローです。ダウンロードには Ashby の収集プログラム、PostgreSQL のスキーマ、無効状態の n8n ワークフローが含まれます。架空のデータから4件の集計アラートを生成します。アカウントを接続する前に、各アラートの根拠を確認できます。

## サンプルを実行する

ダウンロードを展開し、Python 3.10 以降で `python3 -B check_fixture.py` を実行してください。次のコマンドは、2つの検出処理が読み込むスナップショットを表示します。

```sh
python3 -B ashby_adapter.py --config config.example.json --fixture fixtures/ashby-pages.json --as-of 2026-11-02
```

指定した日付は、集計に含めない UTC の終了境界です。日次の対象は11月1日、週次の開始は10月26日です。テストデータには Analyst 求人の応募一覧が2ページ、うち1件の応募の履歴が2ページあります。応募がない監視対象求人と、最近追加された求人も含みます。アダプターは架空のレスポンスを10ページ読み、3求人すべてをスナップショットに含めます。

| 想定アラート | テストデータにある根拠 |
|---|---|
| 選考段階の通過率低下 | Screen からの完了した遷移4件のうち、Onsite に進んだのは1件です。通過率25%は、設定した基準平均75%から標準偏差10ポイントの2倍を引いた値を下回ります。 |
| 完了した段階の滞在時間 | 完了した Screen 区間の中央値は48時間です。アラート閾値は設定した上限24時間の1.5倍です。 |
| 動きのない求人 | 監視対象の Quiet 求人では7日間に段階への移行も離脱もありません。新しい求人は監視から7日未満のため、アラートはありません。 |
| 採用所要期間の傾向 | 1件の応募が作成から59日後に設定した採用段階に到達し、例の閾値30日を超えました。サンプルの最小採用件数は1件です。 |

`fixtures/expected-alerts.json` に想定ペイロードがあります。1件だけの例は `_README.md` に従って PGlite を設定し、`node check_postgres.mjs --one-alert` を実行してください。動きのない求人を使うこの例では、初回に1件をキューに追加し、2回目の新規追加は0件です。完全な SQL チェックでは採用所要期間の検出を先に、段階の検出を後に実行します。新しいアラートは採用所要期間が1件、段階・求人が3件です。両方を再実行しても追加は0件です。ここでの閾値と小さな標本は判定ルールを示すものです。自社の[採用ファネル指標](/ja/learn/recruiting-funnel-metrics/)に合う基準値と最小標本数を選んでください。

## データソースとデータベースを準備する

`config.example.json` をコピーし、架空の求人 ID、段階 ID、表示名、監視日、基準値、上限をすべて置き換えます。どの後続段階への遷移を前進と数えるかを決めてください。完了し、後続段階を確認できる離脱件数を同じ分母として、条件に合う日次通過率から基準の平均と標準偏差を計算します。判定には20日以上の参照期間と正の標準偏差が必要です。最終更新日が35日より前の基準値は拒否されます。過去データの準備と基準値の更新スケジュールは運用担当者が管理します。

別の収集プログラムが各監視対象求人について [Ashby application.list](https://developers.ashbyhq.com/reference/applicationlist) を、各応募について [application.listHistory](https://developers.ashbyhq.com/reference/applicationlisthistory) を呼び出します。どちらも `candidatesRead` を使うページ分割された POST リクエストです。収集プログラムは段階番号で履歴を並べ、段階 ID とタイムスタンプを使います。ページの欠落、レコードの重複、順序の矛盾があれば収集を中断します。活動件数0を解釈できるのは、収集が最後まで成功した場合です。

`psql` で `schema.sql` を適用し、収集プログラムの `ASHBY_API_KEY` を設定してください。`_README.md` の本番用コマンドを02:00 UTC より前に実行するよう予約します。`--persist` は設定した PostgreSQL 接続を使い、完全なスナップショットを1件保存します。テーブルは `hfa.snapshots` と `hfa.alerts` です。同一のスナップショットは再投入できます。同じ日付で内容が異なる場合は確認が必要です。保存する集計には候補者名、メールアドレス、応募 ID を含めません。外部サービスへ渡す前に求人の表示名を確認してください。

## 2つの検出処理と配信を接続する

`hiring-funnel-anomaly-n8n.json` を [n8n](/ja/tools/n8n/) にインポートします。PostgreSQL、Anthropic Header Auth、Slack Header Auth の認証情報を割り当ててください。**Check channel configuration** に、承認済みの段階通知用とリーダー用のチャネル ID を設定します。一時データベースで両方の検出処理が期待するテスト行を返すまで、ワークフローは無効状態に保ちます。収集プログラムは n8n の外部で専用の [Ashby](/ja/tools/ashby/) 認証情報を使います。

02:00 UTC の処理は通過率、完了した滞在時間、7日間の求人活動を評価します。通過率には、終了境界より前に連続する次の段階を確認できる完了済みの離脱を数えます。後続段階のない末尾の離脱や、段階番号に欠番がある遷移は対象外です。滞在時間の対象は完了した区間です。アラートは段階の状態を示し、現在待機中の個人を特定するものではありません。03:00 UTC の処理は、応募作成から設定した採用段階への初回到達までの時間を独立して確認します。段階番号0からその採用段階までの履歴が欠けずにそろう場合だけ採用件数に含めます。先頭部分が欠けていると初回採用日を確認できないため、その応募はこの統計から除きます。指標を[採用所要期間](/ja/learn/time-to-fill-vs-time-to-hire/)として扱う前に、自社 ATS でその段階が何を意味するか確認してください。当日のスナップショットがなければ、どちらの処理もエラーを返します。

両スケジュールは同じ送信待ちテーブルに安定したアラートキーを書き込みます。配信処理は検出後と15分ごとに保留行を1件確保します。[Claude](/ja/tools/claude/) は短い説明を作るための集計値を受け取り、[Slack](/ja/tools/slack/) は数値、説明、参照キーを受け取ります。返された `delivery_state` と行の `state` を確認してください。配信確認済みの Slack 応答には `ok:true`、チャネル、タイムスタンプが含まれます。`ok:false` と `channel_not_found` の組み合わせのように拒否を確定できる場合は、配信失敗を記録します。Slack によると、`internal_error` と `fatal_error` は一部の処理が成功してから返る場合があります。これらのエラー、未知のコード、不完全な確認応答、送信タイムアウトでは、受理の有無は未確定です。再試行を判断する前に、チャネル内で参照キーを探してください。未確定の送信は確認用に保留します。[Slack の応答仕様](https://api.slack.com/methods/chat.postMessage)。

## 検証と運用コスト

12件のオフライン Python チェックは、ページ分割、無効な入力、日付境界、応募のない求人、エクスポート構造を対象にしています。同梱の SQL は架空のレコードを使い、PGlite 経由の PostgreSQL 18.6 と、独立したネイティブ PostgreSQL 18.4 で実行しました。テストでは両スケジュールの処理経路、アラートの正確な内容、再実行を確認しました。PGlite のチェックには、配信行のリース、確認済み応答、確定した拒否、受理の有無が未確定の場合も含まれます。変更していないエクスポートを n8n 2.45.7 にインポートできました。CLI での7回の実行には、手動トリガー、ローカルのテスト認証情報、ループバック上のモデル・Slack エンドポイントを設定したコピーを使いました。実際の SQL、Code、HTTP ノードは、模擬説明4件と確認済みの模擬投稿4件を処理し、各チャネルに2件ずつ届きました。段階、採用、配信の処理を再実行しても、新しい呼び出しやアラートは0件でした。テストデータ用のコマンドは README にあります。指定時刻でのスケジュール起動と実サービスのアカウントは、運用担当者が別途確認する必要があります。

予算には、監視対象求人ごとに走査する応募件数と履歴ページ数、PostgreSQL の保存領域、n8n の実行回数、確保したアラートに対するモデル呼び出しを含めてください。4件の例で初回送信がすべて成功する場合、説明4件と Slack 投稿4件を要求します。送信前の再試行でモデル使用量が増える場合があります。費用や応答時間の目標を決める前に、環境内の実際のトークン数、配信遅延、担当者の確認時間を測ってください。

基準値、配信先、フォローアップの責任者がいない場合は、表計算か既存の ATS レポートを使ってください。段階定義が安定し、確認担当者が決まった時点で検出処理を改めて評価します。出力は採用業務の集計結果を調べるためのものです。グラフに ATS を変更する処理はありません。
