Un flow n8n qui écoute les nouvelles candidatures [Ashby](/fr/tools/ashby/), récupère le dossier candidat plus la rubrique des critères indispensables du poste, demande à [Claude](/fr/tools/claude/) de scorer la candidature par rapport à la rubrique avec des preuves citées depuis le CV, et route le résultat vers l'un des trois canaux Slack : `#review-needed` (la majorité), `#fast-track` (décile supérieur, par score agrégé et récence), ou `#surfaced-not-rejected` (en dessous du seuil mais maintenu visible — le flow ne rejette jamais automatiquement). Remplace l'heure quotidienne d'élagage de boîte mail du recruteur par une file d'attente Slack classée qui prend 12 à 15 minutes à parcourir.

## Quand l'utiliser

- Vous recevez ≥30 candidatures inbound par poste par semaine, et le recruteur passe plus d'une heure par jour à lire des CVs qui ne correspondent majoritairement pas.
- Le poste a une rubrique écrite avec des ancres comportementales par dimension (correspondance de compétences, niveau, localisation/autorisation de travail, probabilité de réponse). Le modèle de rubrique se trouve dans le `_README.md` du bundle. Sans elle, le flow score sur des impressions subjectives.
- Vous utilisez [Ashby](/fr/tools/ashby/) ou un autre ATS qui envoie un webhook par candidature. Greenhouse, Lever, Workable conviennent tous ; le nœud d'intake du flow s'échange proprement. Les plateformes ATS en polling uniquement fonctionnent mais avec un plancher de latence de 5 minutes.
- Un recruteur parcourt la file `#review-needed` au moins quotidiennement et dispose de chaque entrée. Le flow ne déplace pas les candidats vers une étape dans l'ATS.

## Quand NE PAS l'utiliser

- **Rejet automatique dans la boucle.** Le flow classe et route ; il ne rejette jamais. Câbler une action `reject` à un seuil de score transforme ceci en prise de décision automatisée — ce qui déclenche les obligations d'audit de biais de la Local Law 144 de NYC dans l'année suivant la mise en production, et les obligations de système à haut risque de l'Annexe III de l'EU AI Act pour tout candidat résident UE. Le troisième seau du flow (`#surfaced-not-rejected`) existe précisément pour que le recruteur voie qui aurait été rejeté et puisse invalider.
- **Données démographiques comme entrée de scoring.** Le flow refuse de scorer sur le nom, la photo, le nom d'école comme signal isolé, l'adresse, l'âge inféré de l'année de diplôme, les pronoms de genre, les pénalités pour lacunes d'emploi, ou le « culture fit » sans ancres comportementales. La liste de vérification équité dans le `_README.md` du bundle s'exécute comme pré-vol sur la rubrique.
- **Remplacer le jugement du recruteur sur les cas limites.** Un score agrégé dans les 15 % du seuil route vers `#review-needed`, pas vers l'un ou l'autre des extrêmes. C'est une marge de discrétion délibérée.
- **Postes où vous recevez moins de 10 candidatures par semaine.** Le triage manuel est plus rapide que l'ajustement d'une rubrique et d'une file Slack. Le coût de configuration du flow (60 minutes plus la rédaction de rubrique) se justifie à 30 candidatures par semaine, pas à 5.
- **Postes confidentiels / exécutifs.** Posture de consentement différente. Chaîne d'audit différente. Routage différent — ceux-ci vont directement vers un recruteur nommé, pas dans un canal Slack partagé.

## Configuration

1. **Importez le flow.** Déposez `apps/web/public/artifacts/inbound-applicant-triage-n8n/inbound-applicant-triage-n8n.json` dans votre instance n8n. Chaque nœud porte `notesInFlow: true` pour que les notes dans le canvas expliquent les choix.
2. **Câblez les credentials.** Le flow en nécessite trois : `PLACEHOLDER_ASHBY_CRED_ID` (clé API Ashby, scope lecture uniquement), `PLACEHOLDER_ANTHROPIC_CRED_ID` (clé API Claude), `PLACEHOLDER_SLACK_CRED_ID` (token bot Slack avec `chat:write` pour les trois canaux). Chaque section dans `_README.md` indique où trouver la valeur.
3. **Rédigez la rubrique.** Par poste, écrivez un fichier JSON sous `n8n/data/rubrics/<role-slug>.json` avec les quatre dimensions (compétence, niveau, localisation, probabilité-de-réponse) et des ancres comportementales par dimension. Le flow recherche la rubrique par `role_slug` depuis le payload de candidature Ashby. Aucune rubrique pour un poste → le flow s'interrompt avec une entrée de log `missing_rubric` plutôt que de scorer sur des valeurs par défaut.
4. **Configurez les seuils de routage.** Dans le nœud IF `Route by Aggregate` : `aggregate >= 16` route vers `#fast-track`, `12-15` vers `#review-needed`, tout ce qui est en dessous de 12 vers `#surfaced-not-rejected`. Ajustez après une semaine de test à blanc.
5. **Test à blanc sur un poste clôturé.** Rejouez la dernière semaine de candidatures pour un poste que vous avez sourcé manuellement. Comparez le seau `#fast-track` du flow à votre liste réelle de passage en écran téléphonique. Ajustez les ancres de rubrique si elles divergent — les ancres, pas le modèle, sont généralement fautives.
6. **Activez le déclencheur.** Passez le webhook Ashby de `disabled` à `enabled` uniquement après que le test à blanc semble correct. Le trafic webhook en production est plus difficile à déboguer que l'historique rejoué.

## Ce que le flow fait

Huit nœuds, dans l'ordre. Le flow maintient les pré-vols équité et les filtres déterministes avant l'appel LLM, parce que laisser le modèle libre sur un payload contaminé produit un scoring rapide, confiant et inutilisable.

1. **Ashby Webhook** — reçoit les événements `application.created`. La signature du webhook est vérifiée à l'étape suivante ; un payload non vérifié est abandonné.
2. **Verify Signature** — HMAC-SHA256 contre le secret webhook configuré. Signature incorrecte → log + arrêt. La vérification de signature est non optionnelle parce que les webhooks Ashby sont accessibles depuis l'internet ouvert.
3. **Fetch Application + Rubric** — extrait le dossier complet candidat + candidature depuis `/candidate.info` (Ashby est POST uniquement, même pour les lectures — voir le `_README.md` du bundle), et charge le fichier de rubrique du poste. S'interrompt sur `missing_rubric` au lieu de retomber sur un défaut.
4. **Fairness Pre-Flight** — exécute la rubrique à travers une liste de vérification de proxies de classe protégée. Scoring par prestige d'école, filtrage par nom, pénalités pour lacunes d'emploi, présence de photo, « culture fit » sans ancres → arrêt et remontée à l'auteur de la rubrique. Le choix d'échouer avant l'appel LLM est intentionnel : une rubrique biaisée chargée dans une API de scoring laisse une entrée de log qui compte déjà comme traitement automatisé au sens de l'art. 22 RGPD.
5. **Deterministic Pre-Filter** — vérifie l'autorisation de travail par rapport aux exigences de localisation du poste, abandonne les candidatures de la liste des récemment rejetés (période silencieuse de 6 mois), confirme que la candidature dispose des documents requis (CV, lettre de motivation optionnelle). Ces filtres sont auditables et le LLM ne les re-juge pas.
6. **Claude Score** — envoie rubrique + CV + données du formulaire de candidature à Claude. Renvoie un objet JSON avec des scores par dimension 1 à 5, une chaîne de preuve verbatim par dimension au-dessus de 1, et un agrégé. Les scores sans chaîne de preuve sont par défaut à 1. L'exigence de preuve est ce qui maintient le modèle ancré dans le texte du CV plutôt que d'inférer depuis le nom ou l'école.
7. **Route by Aggregate** — nœud IF. Trois branches par fourchette de score comme défini à l'étape 4 de la configuration.
8. **Slack Notify + Audit Append** — poste sur le canal Slack approprié avec un lien vers la page candidat Ashby, les extraits de preuve par dimension, et un lien `view-rubric`. Ajoute une ligne JSONL à `audit/<YYYY-MM>.jsonl` avec `application_id`, `role_slug`, `rubric_sha256`, scores par dimension, agrégé, route, modèle. Pas de données personnelles. Le journal d'audit est ce qui rend une enquête NYC LL 144 ou EU AI Act survivable.

## Réalité des coûts

Pour 100 candidatures scorées, sur Claude Sonnet 4.5 :

- **Tokens API Anthropic** — typiquement 8 à 12 000 tokens d'entrée par candidature (rubrique ~1 000 + CV + données de formulaire) et 400 à 700 tokens de sortie (JSON scoré + preuves). Au tarif catalogue Sonnet 4.5, cela atterrit à environ 0,05 à 0,08 $ par candidature. Une équipe scorant 1 000 candidatures inbound par semaine dépense 50 à 80 $ par semaine en coût de modèle.
- **Coût n8n** — n8n auto-hébergé est gratuit en conteneur. Le plan Starter de n8n Cloud couvre ~5 000 exécutions de workflow par mois à 20 $ ; les équipes à volume moyen (>5 000/semaine) ont besoin de Pro ou auto-hébergé.
- **Quota API Ashby** — appels en lecture uniquement. Le flow fait 1 `/candidate.info` par candidature ; bien en dessous de la limite par défaut d'Ashby de 100 req/min.
- **Temps du recruteur** — le gain. Lire manuellement 100 candidatures prend ~8 heures ; parcourir la file Slack `#review-needed` avec les preuves et liens pré-préparés prend ~20 à 30 minutes. La file fast-track prend encore 5 à 10 minutes pour une prise de contact plus soignée.
- **Temps de configuration** — 60 minutes pour le flow lui-même, plus 30 à 60 minutes par poste pour la rubrique. La rubrique est le coût structurant ; la réutilisation entre familles de postes l'amortit.

## Métriques de succès

Suivez trois chiffres par poste par mois, dans l'ATS :

- **Taux de passage en écran depuis `#fast-track`** — devrait être ≥75 % sur une rubrique calibrée. En dessous, la rubrique ou le seuil est trop lâche ; resserrez les ancres avant d'augmenter le seuil.
- **Taux de passage en écran depuis `#review-needed`** — devrait être de 25 à 40 %. S'il descend sous 20 %, la marge de discrétion est trop large et vous lisez trop. S'il monte au-dessus de 50 %, le seuil fast-track est trop élevé et des candidats qualifiés sont manqués.
- **Temps depuis la candidature jusqu'au premier contact recruteur** — devrait passer de jours à moins de 4 heures. C'est la métrique d'expérience candidat, et c'est ce qui rend le flow défendable auprès du responsable TA.

## Alternatives

- **vs le scoring natif d'Ashby (ou Greenhouse Predictive Hire)** — le scoring natif ATS convient pour la question binaire « probabilité de correspondance », mais le score est une boîte noire et la rubrique n'est pas la vôtre. Choisissez le flow si vous avez besoin d'un score par dimension avec des preuves verbatim (défendable au titre de NYC LL 144), une rubrique que vous versionnez, ou un modèle que vous pouvez changer. Choisissez le natif ATS si votre équipe ne maintiendra pas la rubrique.
- **vs [Eightfold](/fr/tools/eightfold/) / [Findem](/fr/tools/findem/) inbound matching** — ce sont des produits plus profonds : ils re-scorent par rapport à vos recrutements historiques, gèrent l'outbound, possèdent un graphe de candidats. Choisissez-les si le budget soutient le jeu de plateforme et que vous voulez un produit managé. Choisissez le flow si vous voulez la rubrique et le journal d'audit dans votre repo et que le reste de votre stack est déjà câblé.
- **vs script Python DIY interrogeant l'API Ashby** — même qualité de scoring si vous construisez le prompt soigneusement, mais vous construisez aussi la vérification de signature webhook, le pré-vol équité, le chargeur de rubrique, le journal d'audit, le routage Slack, et l'UX de débogage n8n vous-même. Le bundle les inclut.
- **vs statu quo (le recruteur lit tout)** — le manuel est correct pour moins de 10 candidatures/semaine par poste, où une rubrique est une surcharge et la tête du recruteur est déjà calibrée. Le flow justifie son coût de configuration sur les postes qui scalent.

## Points de vigilance

- **Amplification des biais.** *Protection :* le pré-vol équité à l'étape 4 interrompt le flow si la rubrique contient des proxies de classe protégée. Le journal d'audit capture `rubric_sha256` par candidature scorée, donc la rubrique utilisée à une date donnée est reproductible lors d'un examen [EU AI Act](/fr/learn/eu-ai-act-for-legal-teams/) ou NYC Local Law 144.
- **Replay webhook / double scoring.** *Protection :* la signature webhook Ashby inclut `application.created.id`. Le journal d'audit du flow est indexé sur `application_id` ; une deuxième arrivée est détectée et sautée sans re-scoring.
- **Dérive de l'output du modèle sur les modifications de rubrique.** *Protection :* `rubric_sha256` dans le journal d'audit rend les changements de rubrique entre deux exécutions visibles. Si un score agrégé pour une candidature re-scorée diverge, la différence est dans le hash de la rubrique, pas dans la non-déterminisme du modèle.
- **Dérive vers le rejet automatique.** *Protection :* le flow n'a pas de branche `reject`. Le troisième seau est `#surfaced-not-rejected`, et le message Slack inclut un bouton « promote to review » qui re-route la candidature vers `#review-needed`. Le recruteur est la seule autorité de rejet.
- **Données personnelles du CV dans le message Slack.** *Protection :* le message Slack n'inclut que le prénom du candidat, son titre actuel et les extraits de preuve par dimension (max 200 caractères chacun). Le contenu complet du CV reste dans l'ATS. Les canaux Slack ont une rétention plus courte qu'Ashby ; le flow ne transforme pas Slack en base de données candidats.
- **Risque non testé sur les candidats UE.** *Protection :* le nœud `Verify Signature` du flow vérifie aussi la localisation déclarée de la candidature. Les candidatures avec des codes de localisation de résidents UE routent vers `#review-needed` quel que soit leur score, et le message Slack signale `Candidat UE — confirmez que l'avis de screening IA a été remis`. Le screening IA de résidents UE sans avis est une violation de système à haut risque de l'EU AI Act.
