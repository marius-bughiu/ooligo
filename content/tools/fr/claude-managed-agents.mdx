## Ce que c'est

Claude Managed Agents est le runtime hébergé d'Anthropic pour les agents de longue durée, intégré à la Claude Platform (l'API). Vous définissez un **agent** (modèle, system prompt, outils, serveurs MCP et skills), un **environnement** (le sandbox où il travaille), puis vous lancez une **session**, c'est-à-dire une instance en cours d'exécution de cet agent. Anthropic exécute la boucle de l'agent, le conteneur et les appels d'outils ; vous envoyez les tours utilisateur et recevez des événements en streaming. Le lancement en bêta publique date du 8 avril 2026, et tous les endpoints exigent toujours le header bêta `managed-agents-2026-04-01`, que les SDK ajoutent pour vous. L'accès est activé par défaut sur tous les comptes API.

Chaque session reçoit son propre conteneur Linux neuf, avec les langages courants et les gestionnaires de paquets préinstallés. Le toolset intégré couvre `bash`, la lecture, l'écriture et l'édition de fichiers, `glob`, `grep`, `web_fetch` et `web_search`, tous activés par défaut, et chaque outil peut porter une politique de permission qui attend une approbation. Les serveurs MCP distants se connectent en HTTP streamable. Les identifiants sont rangés dans des **vaults** : tokens OAuth pour les serveurs MCP avec renouvellement automatique, tokens bearer et variables d'environnement que le sandbox ne voit que sous forme de placeholders, remplacés par le vrai secret à la sortie réseau. Depuis mai 2026, outcomes (une grille d'évaluation que l'agent s'applique à lui-même), l'orchestration multi-agents, la mémoire et les webhooks sont en bêta publique ; dreaming et les tunnels MCP vers des serveurs privés restent dans une research preview plus restreinte. Le 12 novembre 2026, Anthropic a ouvert une bêta privée de Managed Agents auto-hébergé, qui exécute tout le service dans votre propre cloud.

La question à laquelle il répond pour une équipe ops : *fait-on tourner des agents headless (un passage nocturne d'hygiène du CRM, un tri des contrats entrants, un agent de synthèse des candidats) sur le runtime d'Anthropic, ou continue-t-on à héberger l'Agent SDK nous-mêmes sur n8n ou sur nos propres workers ?*

## Ce que cela coûte en pratique

La facturation comporte deux lignes. Les tokens sont facturés aux tarifs standard de l'API Claude pour le modèle choisi, avec les multiplicateurs de prompt caching appliqués comme d'habitude. Le runtime coûte **$0.08 par heure de session**, mesuré à la milliseconde et facturé uniquement tant que le statut de la session est `running`. Le temps passé en `idle`, à attendre votre prochain message ou l'approbation d'un outil, n'est pas facturé, et le runtime de session remplace la facturation séparée à l'heure de conteneur pour l'exécution de code. La recherche web dans une session coûte $10 pour 1 000 recherches. Il n'y a ni frais par utilisateur ni frais de plateforme, et la consommation s'impute sur un engagement Anthropic existant.

L'exemple chiffré d'Anthropic, une session d'une heure sur Opus 5.5 avec 50 000 tokens en entrée et 15 000 en sortie, revient à $0.58 : $0.20 en entrée, $0.30 en sortie, $0.08 de runtime. Si 40 000 de ces tokens d'entrée viennent du cache, on descend à $0.428. La leçon pour le budget : le runtime est la petite ligne. Une session qui tournerait réellement 24 heures sur 24 pendant un mois ajouterait environ $58 de runtime ; un passage nocturne de 20 minutes ajoute moins de $1 par mois. Ce sont les tokens du modèle qu'il faut prévoir et plafonner. Deux remises ne s'appliquent pas : il n'existe pas de tarif Batch API pour les sessions, ni de tarif cloud partenaire, puisque le runtime hébergé n'est vendu ni via Bedrock ni via Vertex.

## Idéal pour

- **Les équipes RevOps ou Legal Ops avec un seul ingénieur** qui veulent un agent capable de travailler une heure dans un sandbox, d'appeler le CRM ou le CLM via MCP et de rendre compte, sans monter d'abord une flotte de conteneurs, une file de jobs et un coffre à secrets.
- **Les équipes déjà engagées sur l'API Claude** qui intègrent un agent dans un outil interne ou un produit, et pour qui les frais de runtime et le tracing de la console remplacent des semaines de code d'orchestration. Les clients de lancement d'Anthropic (Notion, Rakuten, Asana, Sentry) disent avoir livré en « semaines au lieu de mois » ; ce sont des chiffres publiés par l'éditeur.

## Alternatives, et quand les choisir

- **[Amazon Bedrock](/fr/tools/amazon-bedrock/) avec AgentCore** : l'un des deux leaders en part de marché parmi les plateformes d'agents cloud. Choisissez-le quand l'identité, les données et l'engagement cloud sont chez AWS et que l'agent doit tourner dans votre propre compte. Notez que Claude sur Bedrock n'a pas du tout le runtime Managed Agents.
- **[Microsoft Foundry](/fr/tools/microsoft-foundry/) Agent Service** : l'autre leader. Choisissez-le quand il vous faut un tenant Azure, des identités Entra pour les agents et d'autres modèles que Claude.
- **Héberger vous-même le Claude Agent SDK** sur [n8n](/fr/tools/n8n/) ou vos propres workers : choisissez cette voie quand vous avez besoin dès aujourd'hui de la rétention zéro des données, de l'éligibilité HIPAA ou d'une garantie ferme sur la durée des sessions. Le sandbox, les reprises et les secrets sont à votre charge, et vous ne payez que les tokens.
- **[Claude Cowork](/fr/tools/claude-cowork/)** : choisissez-le quand l'utilisateur est une personne à son bureau, pas un service. Cowork est l'agent de bureau facturé par utilisateur ; Managed Agents est le runtime API pour le travail headless.
- **[Hermes Agent](/fr/tools/hermes-agent/)** : le nouvel entrant à la croissance la plus rapide côté auto-hébergé, avec environ 263 000 étoiles GitHub neuf mois après sa sortie. Choisissez-le pour un agent résident dans Slack ou Telegram, sur n'importe quel modèle, sans travail d'intégration API.

## Points de vigilance

- **La sortie réseau est ouverte tant que vous ne la fermez pas.** Un environnement créé par l'API sans paramètre réseau passe par défaut en `unrestricted` (le formulaire de la console démarre sur Limited). **Garde-fou :** réglez `networking` sur `limited` avec une liste `allowed_hosts` explicite dans chaque environnement créé par code, et gardez en tête que cette liste régit aussi `web_search` et `web_fetch`.
- **Pas éligible à ZDR ni à HIPAA.** La documentation d'Anthropic indique que le runtime hébergé est hors rétention zéro des données et hors HIPAA, pour toutes ses sous-fonctions. **Garde-fou :** gardez les PHI et tout ce qui relève d'une clause ZDR sur un déploiement auto-hébergé de l'Agent SDK, ou attendez la bêta privée auto-hébergée, seule variante couverte par ZDR.
- **C'est une bêta avec un header daté.** Les endpoints, les types d'événements et les valeurs par défaut peuvent changer, et la documentation ne publie ni durée maximale de session ni limite de concurrence ; les rate limits publiés sont de 300 requêtes de création et 1 200 requêtes de lecture par minute et par organisation. **Garde-fou :** figez les versions du SDK, écrivez les définitions d'agent et d'environnement dans des fichiers appliqués avec la CLI `ant` pour qu'elles vivent dans git, et fixez des plafonds de dépense d'organisation avant la première exécution planifiée.
- **La mémoire persiste d'une session à l'autre.** Les memory stores passent d'une exécution à la suivante, donc un fait erroné enregistré par l'agent continue d'orienter les exécutions suivantes. **Garde-fou :** attribuez à chaque agent de production son propre memory store, relisez son contenu via l'API à fréquence fixe et supprimez les entrées qu'aucune source vérifiée ne soutient.
