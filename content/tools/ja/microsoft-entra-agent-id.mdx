## これは何か

Microsoft Entra Agent ID は、AI エージェントに人間の ID を借りさせるのではなく、エージェント自身の ID を与える Entra ID の一部です。Microsoft のドキュメントでは一般提供済みと説明されています。ディレクトリには 4 つのオブジェクトタイプが追加されます。**エージェント ID ブループリント**（一群のエージェントを作成する元になるテンプレート）、各テナントにおけるブループリントのプリンシパル、**エージェント ID** そのもの、そして任意の **エージェントユーザー** です。エージェントユーザーは、ユーザーしか受け付けないシステムにサインインする必要があるエージェントのためのユーザーアカウントです。すべてのエージェント ID には、技術的なオーナーとは別に、ライフサイクルとアクセスに責任を負う実名の人間である **スポンサー** を設定できます。

これらの ID の上に、Entra は人間に対してすでに運用している統制を適用します。エージェント向けの Conditional Access、エージェント向けの ID Protection のリスク検出、ID Governance のアクセスパッケージとスポンサーのライフサイクルワークフロー、そして休眠中のエージェント ID を見つけ出し、責任者に通知し、無効化する既定の非アクティブポリシーです。

Agent ID は ID レイヤーであって、インベントリではありません。**2026年5月1日** 以降、エージェントのレジストリは [Microsoft Agent 365](/ja/tools/microsoft-agent-365/) にあり、Entra 管理センターのレジストリのブレードは廃止されました。Entra が ID を発行して保護し、Agent 365 がエージェントを一覧化して統治します。

## ops チームがここにたどり着く理由

この問いはたいてい 3 つの問いが同時にやってくる形で現れます。ops のエージェントに専用の Entra ID は必要か、それにはどのライセンスが要るのか、そして Microsoft が移行を進めている Copilot Studio のエージェントはどうなるのか、です。

1 つ目の答えは、無人で記録システムに書き込むエージェントが 1 つでもあるなら「はい」です。作成者のトークンで動くエージェントは、ログ上ではその人として現れ、その人がアクセスできるすべてを引き継ぎ、その人が退職すると動かなくなります。あるいは動き続けます。エージェント ID があれば、別個の監査対象、責任を負うスポンサー、そしてポリシーの対象が手に入ります。

3 つ目の答えは、すでにあなたに代わって決まりつつあります。Message Center の通知 **MC1478488**（2026年9月24日）によると、2026年5月より前に作成された [Copilot Studio](/ja/tools/microsoft-copilot-studio/) のエージェントは、いまもレガシーのアプリ登録の ID で動いている可能性があります。Power Platform Advisor でのセルフサービス移行は **2026年8月24日** に始まり、Agent ID を持たないエージェントの自動移行は **2026年9月** に始まりました。移行は ID をその場で変換するため、エージェントはクライアント ID を保持し、コネクタは引き続き解決されます。[Microsoft Foundry](/ja/tools/microsoft-foundry/) のエージェントには自動で Agent ID が付与されます。Microsoft の外で作られたエージェント、つまり [n8n](/ja/tools/n8n/)、[Amazon Bedrock](/ja/tools/amazon-bedrock/)、コンテナ内のあらゆるものは、Entra Auth SDK のサイドカーか、ワークロード ID フェデレーションを通じて ID を取得します。後者はシークレットを保存せずに AWS や Google Cloud のトークンを交換します。

## 価格の実態

Microsoft の製品ページでは、Agent ID は 2 通りの方法で販売されています。

- **Microsoft Agent 365、1 ユーザーあたり月額 15.00 USD**、年額払い。
- **Microsoft 365 E7、1 ユーザーあたり月額 99.00 USD**（Teams なしで 90.45 USD）。Agent 365 と Microsoft Entra Suite がバンドルされています。

お金を払う対象は統制です。Microsoft Learn によると、エージェント向けの Conditional Access とエージェント向けの ID Governance は、いずれも E7、または Agent 365 ライセンスと少なくとも Entra ID P1 か Microsoft 365 E3 の組み合わせを必要とします。通知 **MC1395007** は、2026年7月から8月にかけて Agent 365 と E7 に 2 つのサービスプラン、Entra Conditional Access for Agents と Entra ID Protection for Agents を追加し、これらのライセンスのいずれも持たずにこれらの機能を使っているテナントは、使い続けるためにいずれかを購入する必要があるとしています。

単位はエージェントではなく人間です。**従業員 200 人の E3 企業** の場合、Agent 365 の追加分は 15 USD × 200 = **年間 36,000 USD** です。サインイン済みユーザーの代理として動くエージェントについては、そのユーザー自身のライセンスも関係します。Conditional Access はユーザーのトークンに対して評価されるため E3 が必要で、ID Protection には E5 が、それらのエージェント向けの ID Governance には Entra ID Governance または Entra Suite が必要です。アドオンを飛ばして E7 に移る企業は 99 USD × 200 = **年間 237,600 USD** を支払うことになり、これは E7 に含まれるそれ以外のすべても欲しい場合にしか意味がありません。

## こんなチームに向く

**E3 以上の Microsoft 365 テナント** の IT または ID 担当のリーダーで、ops チームがすでに Copilot Studio、Foundry、n8n でエージェントを動かしている場合です。文句なしに勝つケースは、RevOps や legal ops のエージェントが、セッションに人間がいない状態で CRM や契約リポジトリに書き込み、コンプライアンスレビューで、どの ID がそれぞれの変更を行ったのか、誰がスポンサーなのか、どのポリシーが管理外のネットワークからのアクセスをブロックするのかを問われる場面です。

## 向かないケース

Google Workspace を使っているチーム、または ID プロバイダーが Okta のチームです。ユーザーが別の場所で認証しているエージェントを統治するために Entra を導入することになります。静的なキーで SaaS の API を呼び出すエージェントに対する答えでもありません。Microsoft 自身のドキュメントが、API キーは Entra の認証を完全に迂回するため、Conditional Access のポリシーは一切適用されないと述べています。

## 代替との比較

- **[Okta](/ja/tools/okta/)** — ワークフォース ID におけるもう一方のシェアリーダーです。Agent SSO は 2026年8月24日に、コアの SSO プランの中で追加費用なしで GA となり、Cross App Access を通じて短命なトークンを発行します。Okta for AI Agents は別の見積もり制のサブスクリプションです。従業員がすでに Okta でサインインしていて、重要なエージェントが Microsoft 以外の SaaS にアクセスするなら Okta を選んでください。エージェントが Copilot Studio や Foundry で作られているなら Entra Agent ID を選んでください。どの IdP を好むかに関係なく、それらのエージェントには Entra の ID が発行されるからです。
- **[Rippling](/ja/tools/rippling/) AI Governance** — 最も動きの速い新規参入者で、2026年8月に HRIS の上に MCP ゲートウェイとエージェント ID を載せてローンチしました。Rippling が記録システムであり、別の ID ベンダーを使わずにエージェントのアクセスを雇用状態に連動させたい場合に選んでください。
- **[Zenity](/ja/tools/zenity/)、[Runlayer](/ja/tools/runlayer/)、[Obot](/ja/tools/obot/)** — ID プロバイダーではなく、ツール呼び出しの時点でエージェントが何をするかを検査するものです。リスクが、プロンプトインジェクションを受けたエージェントによる正当な権限の悪用である場合に追加してください。これは ID では止められません。

## 注意点

- **権限の変更で今月エージェントが壊れる可能性があります。** 通知 **MC1506728** によると、Entra は 2026年11月4日から、エージェントのブループリントのプリンシパルに `AgentIdentity.CreateAsManager` を自動付与するのをやめ、ロールアウトは11月下旬まで続きます。管理者による明示的な付与なしに自分の子 ID を作成するエージェントは、現在 403 で失敗します。**ガード：** Entra の監査ログを、アクターがアプリケーションでターゲットがエージェント ID である「Add Service Principal」イベントで絞り込み、まだ必要としている各ブループリントに Graph の権限を付与してください。
- **代理で動くエージェントは、エージェント対象のポリシーをすり抜けます。** エージェント ID を対象とする Conditional Access のポリシーは、そのエージェントがユーザーの代理として行うリクエストをカバーしません。それらはユーザーのポリシーに従い、ID Protection はリスクをユーザーに帰属させます。**ガード：** 自律エージェント、代理（on-behalf-of）フロー、エージェントユーザーという 3 つのアクセスパターンごとに別々のポリシーを書き、それぞれを適用前にレポート専用モードでテストしてください。
- **移行が終わるまで ID タイプが 2 種類あります。** まだアプリ登録で動いている Copilot Studio のエージェントは、エージェント ID 向けに書かれたポリシーの対象外です。**ガード：** Power Platform Advisor の推奨事項を実行し、まず重要度の低いエージェントを少数だけ移行し、チャネルとコネクタを検証し、問題が起きたものにはエージェント単位のロールバックを使ってください。
- **ブループリントへのポリシーは、後から作成されるエージェントにも及びます。** それがブループリントの目的であり、同時に一群のエージェントを誤ってまとめてブロックしてしまう原因にもなります。**ガード：** 新しいポリシーはまず単一のエージェント ID を対象にし、1 週間クリーンなサインインログが続いてから初めてブループリントへ広げてください。
