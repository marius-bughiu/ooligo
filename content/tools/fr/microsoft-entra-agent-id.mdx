## Ce que c'est

Microsoft Entra Agent ID est la partie d'Entra ID qui donne à un agent IA sa propre identité au lieu de le laisser emprunter celle d'un humain. La documentation de Microsoft le décrit comme disponible en version générale. Il ajoute quatre types d'objets à l'annuaire : un **agent identity blueprint** (le modèle à partir duquel une famille d'agents est créée), le principal du blueprint dans chaque tenant, l'**identité d'agent** elle-même, et un **agent user** facultatif, un compte utilisateur pour les agents qui doivent se connecter à des systèmes n'acceptant que des utilisateurs. Chaque identité d'agent peut porter un **sponsor** — un humain nommément désigné, responsable de son cycle de vie et de ses accès — distinct de ses propriétaires techniques.

Sur ces identités, Entra applique les contrôles que vous exploitez déjà pour les personnes : Conditional Access pour les agents, détections de risque ID Protection pour les agents, access packages et workflows de cycle de vie des sponsors dans ID Governance, ainsi qu'une politique d'inactivité par défaut qui repère les identités d'agents dormantes, prévient les responsables et les désactive.

Agent ID est la couche d'identité, pas l'inventaire. Depuis le **1er mai 2026**, le registre des agents se trouve dans [Microsoft Agent 365](/fr/tools/microsoft-agent-365/), et les blades de registre du centre d'administration Entra ont été retirés. Entra émet et sécurise l'identité ; Agent 365 répertorie et gouverne l'agent.

## Pourquoi les équipes ops arrivent ici

La question arrive généralement sous la forme de trois questions à la fois : nos agents ops ont-ils besoin de leurs propres identités Entra, quelle licence cela exige-t-il, et qu'advient-il des agents Copilot Studio que Microsoft est en train de migrer ?

La première réponse est oui, dès qu'un agent écrit sans supervision dans un système de référence. Un agent qui tourne avec le jeton de son créateur apparaît dans les logs sous l'identité de cette personne, hérite de tout ce à quoi elle a accès, et cesse de fonctionner — ou continue de fonctionner — quand cette personne s'en va. Une identité d'agent vous donne un sujet d'audit distinct, un sponsor qui en répond et une cible pour les politiques.

La troisième réponse est déjà en train d'être tranchée pour vous. L'avis du Message Center **MC1478488** (24 septembre 2026) indique que les agents [Copilot Studio](/fr/tools/microsoft-copilot-studio/) créés avant mai 2026 peuvent encore fonctionner avec des identités héritées issues d'inscriptions d'applications ; la migration en libre-service a démarré dans Power Platform Advisor le **24 août 2026**, et la migration automatique des agents sans Agent ID a commencé en **septembre 2026**. La migration convertit l'identité sur place, de sorte que l'agent conserve son ID client et que les connecteurs continuent de se résoudre. Les agents [Microsoft Foundry](/fr/tools/microsoft-foundry/) reçoivent automatiquement un Agent ID. Les agents construits en dehors de Microsoft — [n8n](/fr/tools/n8n/), [Amazon Bedrock](/fr/tools/amazon-bedrock/), tout ce qui tourne dans un conteneur — en obtiennent un via le sidecar Entra Auth SDK ou la fédération d'identités de charge de travail, qui échange un jeton AWS ou Google Cloud sans stocker de secret.

## La réalité des prix

La page produit de Microsoft vend Agent ID de deux façons :

- **Microsoft Agent 365 à $15.00 par utilisateur et par mois**, payé annuellement.
- **Microsoft 365 E7 à $99.00 par utilisateur et par mois** ($90.45 sans Teams), qui regroupe Agent 365 et la Microsoft Entra Suite.

Ce que vous payez, ce sont les contrôles. Microsoft Learn indique que Conditional Access pour les agents et ID Governance pour les agents exigent chacun soit E7, soit une licence Agent 365 associée au minimum à Entra ID P1 ou Microsoft 365 E3. L'avis **MC1395007** a ajouté deux plans de service — Entra Conditional Access for Agents et Entra ID Protection for Agents — à Agent 365 et E7 entre juillet et août 2026, et précisait que les tenants utilisant ces fonctionnalités sans l'une de ces licences doivent en acheter une pour les conserver.

L'unité, c'est l'humain, pas l'agent. Pour une **entreprise en E3 comptant 200 salariés**, Agent 365 ajoute $15 × 200 = **$36,000 par an**. Pour les agents qui agissent au nom d'un utilisateur connecté, la licence propre de l'utilisateur compte aussi : Conditional Access est évalué sur le jeton de l'utilisateur et exige E3, ID Protection exige E5, et ID Governance pour ces agents exige Entra ID Governance ou l'Entra Suite. Une entreprise qui fait l'impasse sur le module complémentaire et passe directement à E7 paie $99 × 200 = **$237,600 par an**, ce qui n'a de sens que si vous voulez aussi tout le reste de ce que contient E7.

## Idéal pour

Un responsable IT ou identité dans un **tenant Microsoft 365 en E3 ou au-delà** dont les équipes ops font déjà tourner des agents dans Copilot Studio, Foundry ou n8n. Le cas où il l'emporte sans discussion : un agent RevOps ou Legal Ops écrit dans le CRM ou dans le référentiel de contrats sans humain dans la session, et une revue de conformité demande quelle identité a effectué chaque modification, qui la parraine, et quelle politique la bloque depuis un réseau non géré.

## À éviter si

Votre équipe est sur Google Workspace, ou votre fournisseur d'identité est Okta. Vous adopteriez Entra pour gouverner des agents dont les utilisateurs s'authentifient ailleurs. Ce n'est pas non plus la réponse pour les agents qui appellent des API SaaS avec des clés statiques : la documentation même de Microsoft indique qu'une clé API contourne entièrement l'authentification Entra, si bien qu'aucune politique Conditional Access ne s'applique.

## Face aux alternatives

- **[Okta](/fr/tools/okta/)** — l'autre leader en parts de marché de l'identité des collaborateurs. Agent SSO est passé en disponibilité générale le 24 août 2026 au sein des plans SSO de base, sans surcoût, en émettant des jetons de courte durée via Cross App Access ; Okta for AI Agents est un abonnement distinct, uniquement sur devis. Choisissez Okta quand vos collaborateurs se connectent déjà via Okta et que les agents qui comptent accèdent à des SaaS hors Microsoft. Choisissez Entra Agent ID quand les agents sont construits dans Copilot Studio ou Foundry, car ils reçoivent une identité Entra quel que soit l'IdP que vous préférez.
- **[Rippling](/fr/tools/rippling/) AI Governance** — le nouvel entrant le plus rapide, lancé en août 2026 avec une passerelle MCP et une identité d'agent bâties sur un SIRH. Choisissez-le quand Rippling est le système de référence et que vous voulez lier l'accès des agents au statut d'emploi sans fournisseur d'identité distinct.
- **[Zenity](/fr/tools/zenity/), [Runlayer](/fr/tools/runlayer/), [Obot](/fr/tools/obot/)** — ce ne sont pas des fournisseurs d'identité ; ils inspectent ce que fait un agent au moment de l'appel d'outil. Ajoutez-en un quand le risque est un agent victime d'une injection de prompt qui détourne des permissions légitimes, ce qu'une identité ne peut pas empêcher.

## Points de vigilance

- **Un changement de permission peut casser des agents ce mois-ci.** L'avis **MC1506728** indique qu'Entra a cessé d'accorder automatiquement `AgentIdentity.CreateAsManager` aux principals de blueprints d'agents à partir du 4 novembre 2026, avec un déploiement jusqu'à fin novembre. Les agents qui créent leurs propres identités enfants sans autorisation administrateur explicite échouent désormais avec une erreur 403. **Garde-fou :** filtrez les journaux d'audit Entra sur les événements « Add Service Principal » ayant une application pour acteur et une identité d'agent pour cible, et accordez la permission Graph à chaque blueprint qui en a encore besoin.
- **Les agents on-behalf-of échappent aux politiques ciblant les agents.** Une politique Conditional Access qui cible une identité d'agent ne couvre pas les requêtes que cet agent effectue au nom d'un utilisateur ; celles-ci suivent les politiques de l'utilisateur, et ID Protection attribue le risque à l'utilisateur. **Garde-fou :** rédigez des politiques distinctes pour les trois schémas d'accès — agents autonomes, flux on-behalf-of et agent users — et testez chacune en mode report-only avant de l'appliquer.
- **Deux types d'identité tant que la migration n'est pas terminée.** Les agents Copilot Studio encore sur des inscriptions d'applications ne sont pas couverts par les politiques écrites pour les identités d'agents. **Garde-fou :** exécutez la recommandation de Power Platform Advisor, migrez d'abord un petit lot d'agents non critiques, validez les canaux et les connecteurs, et utilisez le rollback par agent pour tout ce qui casse.
- **Une politique sur un blueprint atteint les agents créés plus tard.** C'est tout l'intérêt des blueprints, et aussi un moyen de bloquer par accident toute une famille. **Garde-fou :** limitez d'abord les nouvelles politiques à une seule identité d'agent et n'élargissez au blueprint qu'après une semaine de journaux de connexion propres.
