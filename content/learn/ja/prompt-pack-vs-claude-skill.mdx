プロンプト パック（プロンプト ライブラリやプロンプト コレクションとも呼ばれます）は、特定のタスクを進めるために Claude に貼り付ける、厳選されたテキスト指示のセットです。Claude スキルは、Claude が自動的に読み込むパッケージ化された指示モジュールで、セッションをまたいで持続し、何も再入力せずに参照ファイル、スクリプト、構造化されたワークフローを呼び出せます。この選択は「構築 vs コピー」の問題です：作業が一度きりまたは低頻度のタスクなら、プロンプト パックが正しく、スキルは過剰設計です。作業が繰り返し発生する高リスクの Ops タスクで、一貫性とチーム配布が重要なら、スキルが適切な単位です。

## そうでないもの

プロンプト パックはスキルではありません。プロンプトは*リアクティブ*です — 各セッションで提供し、Claude がそれをその時点の会話に適用した後は消えます。Notion、Google Doc、または `.txt` ファイルのフォルダーに整理されたプロンプト パックは、Claude のコンテキストに自動的に持続しません。参照ファイルを読み込みません。手動でオーケストレーションせずにサブステップを起動することもできません。

Claude スキルは、SKILL.md ファイルに自然言語の指示が含まれていても、プロンプトではありません。違いはパッケージングと持続性の層にあります：スキルは Claude Code に登録（またはプラグイン経由で共有）されるため、Claude が動的に検出し、関連性があるときに読み込み、チームが基礎ファイルに触れることなく名前で呼び出せます。スキルは、指示と一緒に読み込まれる参照アセット（条項テンプレート、スコアリング ルーブリック、ペルソナシート）もバンドルできます。

## プロンプト パックが得意なこと

プロンプト パックは日常的な Claude 使用の大部分をカバーし、そうあるべきです。プロンプト パックが正しい選択のユースケース：

- **アドホック分析。** データセットを探索したり、ミーティングの文字起こしを要約したり、一度きりのコミュニケーションを下書きしたりしています。今回は特定のフレームを Claude に適用してほしい。また必要になるかどうかわからない。
- **低頻度のタスク。** 四半期ごとの競合分析を実施しているなら？ Notion から貼り付ける適切に書かれたプロンプトは 10 秒で済み、メンテナンス コストもゼロです。
- **新しいワークフローの実験。** スキルとしてパッケージ化することにコミットする前に、プロンプト パックを使えば設定ファイルに触れずに指示セットを反復できます。正しい方法を見つけるためにプロンプト パックを使い、方法が安定したらスキルに変換してください。
- **個人での利用。** プロンプトが一人のワークフロー用で共有しない場合、個人メモ ツールのプロンプト パックで十分です。

プロンプト パックの正しいパターン：プロンプトを丁寧に書き、明確な名前とコンテキスト メモと一緒に保存し、必要なときに取り出す。

## プロンプト パックにできないこと

スキルには、プロンプト パックにない 4 つの機能があります：

1. **貼り付けなしの持続性。** 登録済みのスキルは、何もコピーせずに Claude のコンテキストで常に利用可能です。Claude はスキルが関連性があると検出してそれを読み込みます。日常的なワークフローでは、これが積み重なります：15 の繰り返し分析タスクを実行するチームは 15 の異なるプロンプトをコピーするのをやめます。
2. **バンドルされた参照アセット。** プロンプトは Claude に「標準的な NDA のフォールバック ポジションを適用してください」と伝えられます。スキルは、実行中に Claude が読む参照ファイルとして、それらのフォールバック ポジションを実際に*含んでいます*。スキルは、Claude が先月ユーザーがコピーしたものではなく、そのドキュメントの最新バージョンを使用することを保証します。
3. **チーム配布とバージョン管理。** スキルはリポジトリに存在するか、定義されたバージョンを持つプラグイン経由で共有されます。指示セットを更新すると、スキルを実行するすべてのチームメンバーが更新を受け取ります。プロンプト パックの更新は、全員が新しいテキストを再コピーする必要があります。
4. **順次手順の実行。** スキルは、明示的なステージ ロジックを持つ多段階のメソッドを定義できます — たとえば：契約書を読む、リスク条項を特定する、ルーブリックに対して各条項を採点する、構造化された JSON 出力を返す。同じ手順をプロンプトから実行するには、ユーザーがターン間で各ステップを手動でオーケストレーションする必要があります。

## 変換のトリガー：プロンプト パックからスキルへ移行するタイミング

次の 3 つの条件が満たされたらプロンプト パックからスキルに移行してください：

1. **タスクがあなたまたはチームのいずれかにとって少なくとも週次で繰り返す。** 週次頻度を下回ると、スキルのメンテナンス オーバーヘッド（メソッドが変わったときに更新すること）は割に合いません。
2. **一貫性エラーが発生した。** 各人がプロンプトのわずかに異なるバージョンを持っていたり、ステップを忘れたりするため、同じタスクがユーザーやセッション間で異なる出力を生成します。スキルはコピー&ペーストの発散を排除します。
3. **メソッドが安定している。** 良い出力がどのように見えるか、どの失敗モードを防ぐか、どの参照資料が必要かを知るのに十分な回数タスクを実行しました。実験的なプロンプトを早すぎるうちにスキルに変換すると、スキルが移動するターゲットになります。

実用的なチェック：同じプロンプトを 20 回以上コピーして「バージョン 2」「バージョン 3」のコピーを管理し始めていたら、すでに質の悪いスキルを運用しています。正式化してください。

## コストとメンテナンスの比較

| 次元 | プロンプト パック | Claude スキル |
|---|---|---|
| セットアップ時間 | 数分 | 1〜4 時間（SKILL.md の執筆 + 参照ファイル + テスト） |
| 使用ごとの摩擦 | 各セッションにプロンプトを貼り付ける | ゼロ — Claude が自動的に読み込む |
| チーム配布 | 各自が自分のコピーを維持 | 単一ソース。一度更新 |
| 参照アセット | ユーザーが貼り付けるか記憶に頼る | バンドル済み。常に最新 |
| メソッドのバージョン管理 | アドホック（v1、v2、final、FINAL） | Git 追跡 |
| トークンコスト | 各セッションでプロンプトの全トークン | アイドル時 30〜50 トークン。アクティブ化時 ~5,000 |

スキルへの設定投資は、タスクが ~20〜30 回以上実行されると回収できます。その閾値を下回る場合、プロンプト パックはどの指標においても速いです。

## よくある落とし穴

- **スキルを早く構築しすぎる。** 良い出力がどのように見えるかまだわからない場合、プロンプトをスキルとしてパッケージ化すると、テキスト ファイルを更新するだけでなく毎週 SKILL.md を編集することになります。メソッドが安定するまで待ってください。
- **プロンプト パックを有効期限を超えて維持する。** Notion データベースに 40 のプロンプトがあり、チームの 3 人が同じプロンプトの異なるバージョンを使用している場合、スキルのオーバーヘッドをそのメリットなしに抱えています。高頻度のものを変換してください。
- **スキルの作成を文章の練習として扱う。** SKILL.md の重要なセクションは「いつ呼び出さないか」のブロックと出力フォーマットの仕様で、入門的な説明ではありません。出力フォーマットを正確に指定しないスキルは、指示がどれほど適切に書かれていても、一貫性のない出力を生成します。
