## O que é

O Microsoft Entra Agent ID é a parte do Entra ID que dá a um agente de IA a própria identidade, em vez de deixá-lo pegar emprestada a de uma pessoa. A documentação da Microsoft o descreve como disponível para uso geral. Ele adiciona quatro tipos de objeto ao diretório: um **blueprint de identidade de agente** (o modelo a partir do qual uma família de agentes é criada), a entidade de serviço do blueprint em cada tenant, a **identidade de agente** em si e um **usuário de agente** opcional, uma conta de usuário para agentes que precisam fazer login em sistemas que só aceitam usuários. Cada identidade de agente pode ter um **sponsor** — uma pessoa nomeada, responsável pelo ciclo de vida e pelo acesso dela — separado dos proprietários técnicos.

Em cima dessas identidades, o Entra aplica os controles que você já usa para pessoas: Conditional Access para agentes, detecções de risco do ID Protection para agentes, pacotes de acesso e workflows de ciclo de vida do sponsor no ID Governance, e uma política padrão de inatividade que encontra identidades de agente paradas, notifica os responsáveis e as desativa.

O Agent ID é a camada de identidade, não o inventário. Desde **1º de maio de 2026**, o registro de agentes fica no [Microsoft Agent 365](/pt-BR/tools/microsoft-agent-365/), e as telas de registro do centro de administração do Entra foram desativadas. O Entra emite e protege a identidade; o Agent 365 lista e governa o agente.

## Por que os times de operações chegam aqui

A pergunta costuma chegar como três perguntas de uma vez: nossos agentes de operações precisam de identidades próprias no Entra, qual licença isso exige, e o que está acontecendo com os agentes do Copilot Studio que a Microsoft está migrando?

A primeira resposta é sim, se algum agente escreve em um sistema de registro sem supervisão. Um agente rodando com o token de quem o criou aparece nos logs como essa pessoa, herda tudo o que essa pessoa consegue acessar e para de funcionar — ou continua funcionando — quando essa pessoa sai. Uma identidade de agente te dá um sujeito de auditoria separado, um sponsor que responde por ele e um alvo para políticas.

A terceira resposta já está sendo decidida por você. O aviso do Message Center **MC1478488** (24 de setembro de 2026) diz que agentes do [Copilot Studio](/pt-BR/tools/microsoft-copilot-studio/) criados antes de maio de 2026 podem ainda rodar com identidades legadas de registro de aplicativo; a migração self-service começou no Power Platform Advisor em **24 de agosto de 2026**, e a migração automática de agentes sem Agent ID começou em **setembro de 2026**. A migração converte a identidade no lugar, então o agente mantém o client ID e os conectores continuam resolvendo. Agentes do [Microsoft Foundry](/pt-BR/tools/microsoft-foundry/) recebem um Agent ID automaticamente. Agentes construídos fora da Microsoft — [n8n](/pt-BR/tools/n8n/), [Amazon Bedrock](/pt-BR/tools/amazon-bedrock/), qualquer coisa em um contêiner — recebem um por meio do sidecar do Entra Auth SDK ou da federação de identidade de carga de trabalho, que troca um token da AWS ou do Google Cloud sem armazenar um segredo.

## A realidade dos preços

A página do produto da Microsoft vende o Agent ID de duas formas:

- **Microsoft Agent 365 a US$ 15,00 por usuário por mês**, pago anualmente.
- **Microsoft 365 E7 a US$ 99,00 por usuário por mês** (US$ 90,45 sem Teams), que inclui o Agent 365 e a Microsoft Entra Suite.

Você paga pelos controles. O Microsoft Learn afirma que Conditional Access para agentes e ID Governance para agentes exigem, cada um, o E7 ou uma licença do Agent 365 combinada com pelo menos Entra ID P1 ou Microsoft 365 E3. O aviso **MC1395007** adicionou dois planos de serviço — Entra Conditional Access for Agents e Entra ID Protection for Agents — ao Agent 365 e ao E7 entre julho e agosto de 2026, e disse que tenants que usam esses recursos sem uma dessas licenças precisam comprar uma para mantê-los.

A unidade é a pessoa, não o agente. Para uma **empresa no E3 com 200 funcionários**, o Agent 365 acrescenta US$ 15 × 200 = **US$ 36.000 por ano**. Para agentes que agem em nome de um usuário logado, a licença do próprio usuário também conta: o Conditional Access é avaliado contra o token do usuário e precisa de E3, o ID Protection precisa de E5, e o ID Governance para esses agentes precisa de Entra ID Governance ou da Entra Suite. Uma empresa que pula o add-on e vai direto para o E7 paga US$ 99 × 200 = **US$ 237.600 por ano**, o que só faz sentido se você também quiser todo o resto que o E7 inclui.

## Ideal para

Um líder de TI ou de identidade em um **tenant do Microsoft 365 com E3 ou superior** cujos times de operações já rodam agentes no Copilot Studio, no Foundry ou no n8n. O caso em que ele ganha sem discussão: um agente de RevOps ou Legal Ops escreve no CRM ou no repositório de contratos sem nenhuma pessoa na sessão, e uma revisão de compliance pergunta qual identidade fez cada alteração, quem é o sponsor e qual política a bloqueia a partir de uma rede não gerenciada.

## Não é para

Um time no Google Workspace, ou um cujo provedor de identidade é o Okta. Você estaria adotando o Entra para governar agentes cujos usuários se autenticam em outro lugar. Também não é a resposta para agentes que chamam APIs de SaaS com chaves estáticas: a própria documentação da Microsoft diz que uma API key ignora completamente a autenticação do Entra, então nenhuma política de Conditional Access se aplica.

## Comparado às alternativas

- **[Okta](/pt-BR/tools/okta/)** — o outro líder em participação de mercado em identidade da força de trabalho. O Agent SSO entrou em GA em 24 de agosto de 2026 dentro dos planos principais de SSO sem custo adicional, emitindo tokens de curta duração via Cross App Access; o Okta for AI Agents é uma assinatura separada, só sob cotação. Escolha o Okta quando seu pessoal já faz login pelo Okta e os agentes que importam acessam SaaS que não é da Microsoft. Escolha o Entra Agent ID quando os agentes são construídos no Copilot Studio ou no Foundry, porque eles recebem uma identidade do Entra independentemente do IdP que você prefere.
- **[Rippling](/pt-BR/tools/rippling/) AI Governance** — o concorrente que mais rápido se move, lançado em agosto de 2026 com um gateway MCP e identidade de agentes em cima de um HRIS. Escolha-o quando o Rippling é o sistema de registro e você quer o acesso dos agentes amarrado ao status de emprego sem um fornecedor de identidade separado.
- **[Zenity](/pt-BR/tools/zenity/), [Runlayer](/pt-BR/tools/runlayer/), [Obot](/pt-BR/tools/obot/)** — não são provedores de identidade; eles inspecionam o que um agente faz na chamada de ferramenta. Adicione um quando o risco é um agente sob prompt injection usando indevidamente permissões legítimas, algo que uma identidade não consegue impedir.

## Pontos de atenção

- **Uma mudança de permissão pode quebrar agentes este mês.** O aviso **MC1506728** diz que o Entra parou de conceder automaticamente `AgentIdentity.CreateAsManager` às entidades de serviço de blueprints de agentes a partir de 4 de novembro de 2026, com rollout até o fim de novembro. Agentes que criam as próprias identidades filhas sem uma concessão explícita de administrador agora falham com um 403. **Proteção:** filtre os logs de auditoria do Entra por eventos "Add Service Principal" com um ator de aplicativo e um alvo de identidade de agente, e conceda a permissão do Graph a cada blueprint que ainda precisar dela.
- **Agentes on-behalf-of escapam das políticas voltadas a agentes.** Uma política de Conditional Access que tem como alvo uma identidade de agente não cobre as solicitações que esse agente faz em nome de um usuário; essas seguem as políticas do usuário, e o ID Protection atribui o risco ao usuário. **Proteção:** escreva políticas separadas para os três padrões de acesso — agentes autônomos, fluxos on-behalf-of e usuários de agente — e teste cada uma em modo somente relatório antes de aplicar.
- **Dois tipos de identidade até a migração terminar.** Agentes do Copilot Studio ainda em registros de aplicativo não são cobertos por políticas escritas para identidades de agente. **Proteção:** execute a recomendação do Power Platform Advisor, migre primeiro um lote pequeno de agentes não críticos, valide canais e conectores, e use o rollback por agente para qualquer coisa que quebrar.
- **Uma política em um blueprint alcança agentes criados depois.** Esse é o objetivo dos blueprints, e também uma forma de bloquear uma família inteira sem querer. **Proteção:** restrinja novas políticas a uma única identidade de agente primeiro e amplie para o blueprint só depois de uma semana de logs de login limpos.
