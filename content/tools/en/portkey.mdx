## What it is

Portkey is an AI gateway: one OpenAI-compatible endpoint that sits between your apps and agents and the model providers behind them. Teams call Portkey; Portkey holds the provider keys, routes and falls back between models, caches responses, applies guardrails, enforces budgets and rate limits per team, and logs every request with cost and latency. The homepage claims access to 1,600+ LLMs; the docs overview still says 250+, so treat the bigger number as marketing. An MCP gateway puts the same authentication, access control and logging in front of MCP servers, and there is a dedicated gateway setup for [Claude Code](/en/tools/claude-code/).

The core gateway is open source under MIT on GitHub (about 13.4k stars). The hosted control plane adds the observability UI, prompt management, semantic caching, RBAC, SSO and audit logs.

The ops question it answers: agents and automations across RevOps, support and legal now call three or four model providers, finance wants one spend view, security wants PII redaction and one kill switch, and nobody wants to run the gateway themselves.

## What the Palo Alto acquisition changed

Palo Alto Networks announced the deal on April 30, 2026 and closed it on May 29, 2026; the price was not disclosed. On July 16 Palo Alto made the product generally available as **Prisma AIRS AI Gateway**, described as a single gateway for LLM, MCP and agent-to-agent (A2A) traffic tied into Prisma AIRS runtime security and red-teaming.

What that means in practice, as checked on November 22, 2026:

- **The pricing page is gone.** portkey.ai/pricing now redirects to a Palo Alto contact-sales form. Every Contact and Demo button on portkey.ai goes there too.
- **The commitment is thin.** Palo Alto's only public customer promise is that it "will continue to support existing and new Portkey customers". Nothing published says the standalone product keeps its own roadmap or pricing.
- **Air-gapped deployment is no longer offered** to new customers, per Portkey's own feature-comparison page. Existing air-gapped installs remain supported. Managed SaaS and hybrid (gateway in your VPC, control plane hosted by Portkey) remain.
- **The open-source repo has slowed.** The last tagged release on GitHub is v1.15.2 from January. The README still calls Gateway 2.0, which merges the enterprise gateway into open source, a pre-release.

## Pricing

From Portkey's docs feature-comparison page, checked 2026-11-22:

- **Open source:** free, self-hosted, no request limit, no hosted logs.
- **Dev:** free, 10,000 requests a month, no overage, 3-day log retention.
- **Pro:** $49 a month for 100,000 requests, then $9 per extra 100,000 up to 3 million, with 30-day retention and semantic caching. The homepage shows a conflicting "59.99$" tile for 0.5M, so confirm the figure before you budget.
- **Enterprise:** custom. BAA signing, VPC hosting, private tenancy, SCIM and advanced RBAC sit here, and the "Book Call" link now goes to Palo Alto sales.

Real-world band: a single ops team logging a few hundred thousand requests a month stays under $100 a month on Pro. Anything needing SSO, a BAA or VPC hosting is an enterprise security deal, priced alongside Prisma AIRS. Budget a Palo Alto procurement cycle, not a credit-card signup.

## Best for

A platform or AI-enablement team at a company whose security organisation already buys Palo Alto (Prisma, Strata or Cortex), which wants a managed gateway with guardrails, PII redaction and MCP governance, and wants model and agent traffic reported into the same security console.

## Not for

A team that needs a fully self-hosted or air-gapped gateway it controls end to end; new air-gapped deployments are off the table. Not for a small team that wants transparent self-serve pricing a year from now; the public price list already lives in docs rather than on a pricing page. And not for a single-provider shop: if everything runs on [Amazon Bedrock](/en/tools/amazon-bedrock/) or [Microsoft Foundry](/en/tools/microsoft-foundry/), their native quotas and IAM cover most of this.

## Versus the alternatives

- **[LiteLLM](/en/tools/litellm/)**, the open-source gateway most often shortlisted against Portkey. Pick it when you need to run the whole gateway inside your own network and have an engineer to own upgrades. Read its 2026 supply-chain record first.
- **[OpenRouter](/en/tools/openrouter/)**, the fastest-growing hosted router, now owned by Stripe. Pick it when you want one bill across hundreds of models and no gateway policy layer beyond keys and limits.
- **Cloudflare AI Gateway** or **Kong AI Gateway**. Pick these when that vendor already fronts your APIs.
- For tracing and evals rather than routing, pair any gateway with [Langfuse](/en/tools/langfuse/) or [LangSmith](/en/tools/langsmith/).

So is Portkey still the right gateway? Yes if you are a Palo Alto shop: you get a mature gateway that now plugs into the security stack you already pay for. If you are not, the safer default is LiteLLM (self-hosted) or OpenRouter (hosted), because Portkey's standalone pricing and roadmap now depend on a parent whose priority is Prisma AIRS.

## Watch-outs

- **Pricing can change at renewal.** The self-serve price list survives only in docs, and sales now runs through Palo Alto. Guard: lock the per-request rate and log retention for the full term in writing, and get a renewal cap before you route production traffic.
- **Gateway lock-in through prompts and configs.** Prompt templates, routing configs and virtual keys live in Portkey's control plane. Guard: keep prompts in your own repo, call Portkey through the OpenAI-compatible API so you can swap the base URL, and export logs to your own warehouse or OpenTelemetry sink.
- **Logs hold your prompts and responses.** That includes customer and candidate data passing through agents. Guard: ask Portkey to disable request and response body storage (the docs say it can on request), and turn on PII redaction guardrails before go-live.
- **Self-hosting the open-source gateway is not the product.** Prompt management and semantic caching are hosted or enterprise only, and releases have stalled since January. Guard: if self-hosting is a hard requirement, evaluate LiteLLM in parallel rather than counting on Gateway 2.0 shipping.
