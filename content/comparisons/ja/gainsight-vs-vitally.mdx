[Gainsight](/ja/tools/gainsight/) と [Vitally](/ja/tools/vitally/) はともに Customer Success チーム向けに設計されていますが、「CS向けに構築」の意味するところが実際には大きく異なります。Gainsight は市場で最も深い health scoring とプレイブックエンジンを持つ設定可能な Enterprise プラットフォームで、オプションの Product Experience バンドルも提供します。Vitally は Notion に近いコラボレーション画面を持つモダンな CS プラットフォームで、Docs がアカウントデータの隣に存在し、View は柔軟で、非 Admin ユーザーでも自分のダッシュボードを作れます。判断の要点はこうです。最大の設定可能性と PX バンドルが必要か、それとも Admin だけでなく CS チーム全員が毎日実際にツールを使えることが必要か。

## Gainsight が優れている点

- **Health score の設定可能性。** Gainsight のスコアカードビルダーは、製品イベント、サポート履歴、請求サイクル、NPS、コミュニティ活動など実質的にあらゆるデータソースからのシグナルを重み付けできます。Vitally の health scoring は堅実ですが、より固定的です。カスタム次元が少なく、重み付けとしきい値ロジックの柔軟性も限られます。マルチプロダクトの health モデルを構築する Enterprise CS-Ops チームにとって、Gainsight の深度は競合が難しいものです。
- **Gainsight PX バンドル。** Gainsight は CS + Product Experience を単一契約として販売します。PX はアプリ内エンゲージメント（ガイド、アナウンス、オンボーディングチェックリスト、採用調査）を CS が見る同じ health レコードに統合します。この比較において、そのような組み合わせをネイティブに提供する他のプラットフォームはありません。CS モーションとアプリ内エンゲージメントプログラムの両方を運用しているなら、バンドル（通常、個別購入より 15-25 % 安く交渉可能）は真の構造的優位性です。
- **Journey Orchestrator と Rules Engine。** Gainsight は自動化をデータ駆動型トリガー用の Rules Engine と多段階ライフサイクルプログラム用の Journey Orchestrator の 2 つに分割します。この分割はよく複雑だと批判されますが、数十の同時プログラムを持つ大規模 CS チームにとって、データトリガー自動化と人が管理するジャーニーの明示的な分離は運用上有用です。
- **Enterprise ガバナンス。** Gainsight はすべてのティアで SSO、ロールベースのアクセス制御、チームレベルのセグメンテーション、監査ログを提供します。上場企業や SOC 2 監査対象の企業にとって、ガバナンス層は重要です。

## Vitally が優れている点

- **CSM 向け UX。** Gainsight に対して最も多く寄せられる批判は、非 Admin ユーザーがガイダンスなしでプラットフォームを操作しにくいというものです。Vitally の UI デザインは CSM が Admin 層に触れることなく独自のダッシュボードや View を構築できる柔軟性を与えます。プラットフォームを初めて使う CSM は 1 週間以内に生産的になれます。Gainsight は通常、構造化されたオンボーディングが必要です。
- **自動化のアーキテクチャ。** Vitally のプレイブックシステムは、7 種類のトリガータイプと 13 種類のアクション（CSM 割り当て、プロジェクト作成、メール配信、タスク完了を分岐ロジックで組み合わせ可能）を備えた統一インターフェースを使います。Gainsight の Rules Engine と Journey Orchestrator の分割は同様の結果を達成しますが、設定面積が 2 倍必要です。Apollo の CS-Ops マネージャーは Vitally に移行後、Gainsight の Admin チーム相当を 8 から 1 に削減できたと報告しています。
- **コラボレーション Docs。** Vitally のネイティブ Docs 機能により、CSM はアカウントデータの隣に生きたドキュメントを作成できます。QBR 準備、サクセスプラン、ミーティングノートにリアルタイムの顧客データが埋め込まれます。Gainsight は同じワークフローにサードパーティツール（Confluence、Google Docs、Notion）が必要です。アカウントプランを外部ツールに散在させるのではなく CS プラットフォーム内に置きたいチームにとって、Vitally のネイティブ Docs は実際の運用上の摩擦を排除します。
- **Time-to-value。** Vitally の平均 go-live は約 2 ヵ月です。Gainsight の現実的な Enterprise 実装は 8-16 週間で、通常は専任の社内担当者と継続的な認定 Admin サポートが必要です。プラットフォームが完全稼働するまでに 6 ヵ月の余裕を持てないチームにとって、Vitally はより誠実なコミットメントです。
- **すべてのプランで全機能を提供。** Vitally の料金モデルはすべてのティアで完全な機能アクセスを含みます。ゲートされたモジュールも、基本機能に対するプレミアム add-on もありません。Gainsight の AI 機能（Horizon AI）は別途販売され、高度なプレイブック機能にはより高いティアが必要です。

## 価格の現実

Vitally の料金はエンゲージメントモデルベース（Tech-Touch、Hybrid-Touch、High-Touch ティア）でクオートのみですが、公開されている市場データでは 10-15 人の CS チームのミッドマーケット向けデプロイメントが年間 $18,000-50,000 と算定されています。Gainsight の典型的なミッドマーケット価格帯は PX バンドルや Horizon AI を除いて年間 $50,000-100,000 で、両モジュールを含む複雑な Enterprise デプロイメントは年間 $200,000 を定常的に超えます。同等スコープにおける差はおよそ 2-3 倍です。PX バンドルを具体的に検討している場合、統合 Gainsight 契約は通常 Gainsight CS + 別途製品分析ツールより安くなりますが、その優位性はアプリ内エンゲージメントプログラムを実際に運用している場合にのみ現れます。念のために PX に支払うためではありません。どちらのプラットフォームも定価を公表していません。

## 実装工数

Vitally：平均 go-live 約 2 ヵ月、初日からすべての機能が利用可能、メンテナンスには 1 人の Admin またはパートタイムの CS ops リソースで十分。Gainsight：現実的なデプロイメントに 8-16 週間、セットアップ中は専任プロジェクトオーナーが必要、継続的な認定 Admin が必要。Admin 比率の差は具体的です。上記の比率（同等の CS モーションに対する Gainsight 対 Vitally の Admin 相当人数 8:1）は極端なケースですが、方向性として「Gainsight は CSM 1 人あたりより多くの Admin 時間を要する」という主張は G2 の満足度データと一致しています。

## 結論

- **Gainsight を選ぶ**なら、PX バンドル（アプリ内ガイド + CS ヘルスを 1 契約で）が必要で、専任の CS-Ops Admin がおり、Salesforce 上で 300 以上のアカウントを管理し、3 つ以上の異なるデータソースから引き出す health モデルを構築している場合。
- **Vitally を選ぶ**なら、CS チーム全員が毎日プラットフォームを使うことが最優先事項で、QBR docs やサクセスプランのためのサードパーティツールを排除したく、CS-Ops チームが小規模（1-2 人以下）の場合。
- **どちらも選ばない**のは、CS 機能がまだない場合——専任でない CSM が管理する 15 未満のアカウント。その規模では、ネイティブの Salesforce や HubSpot ビューと共有 Notion ワークスペースの方がどちらのプラットフォームより効果的です。

前提条件なしで選ぶなら Vitally を選んでください。Gainsight の設定可能性の優位性は、それを設定する Admin キャパシティがある場合にのみビジネス成果に転化します。$60,000-100,000 ティアで Gainsight を購入したチームの多くは、最終的にプラットフォーム機能の 30-40 % しか使いません。PX が真のユースケースになるか、CS-Ops チームが 2 つの別々の自動化システムを維持できる規模になった時点で Gainsight に切り替えてください。
