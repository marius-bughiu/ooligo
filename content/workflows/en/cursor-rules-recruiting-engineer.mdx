A Cursor rules file (`.cursor/rules/recruiting-engineer.md`) tuned for the in-house recruiting-engineering work patterns: building [ATS](/en/learn/ats-vs-recruiting-crm/) integrations, writing [MCP servers](/en/workflows/mcp-server-ashby-recruiting/) for recruiting AI tools, automating intake forms, and integrating recruiting-tech systems. Encodes the conventions and guardrails that distinguish recruiting-tech engineering from general application engineering.

## What you'll need

- Cursor (latest version with Project Rules support)
- Working recruiting-engineering project — typically TypeScript or Python automation, integration code, or ATS configuration repos
- Familiarity with the recruiting systems being integrated ([Ashby](/en/tools/ashby/), [Greenhouse](/en/tools/greenhouse/), [Lever](/en/tools/lever/), MCP)

## Setup

1. **Create the rules directory.** In your project root: `.cursor/rules/`.
2. **Drop the rule file.** Save the following as `.cursor/rules/recruiting-engineer.md`:

```markdown
# Recruiting engineer conventions

## Audit trail is mandatory
Every read or write against recruiting data systems (ATS, CRM, assessment) must produce an audit log entry with: timestamp, user identity, system accessed, action taken, data scope. Never write code that touches candidate data without an explicit audit log call. If the audit infrastructure doesn't exist, build it before the integration.

## Bias and fairness safety
Code that influences hiring decisions requires explicit handling of bias and fairness concerns. Never:
- Use protected-class attributes as direct decision criteria
- Use proxies (ZIP code, names, school, photo) as scoring features without explicit fairness analysis
- Deploy AI screening to production without bias-audit infrastructure per NYC Local Law 144 / Illinois AVDA / EU AI Act requirements
- Auto-reject candidates without human-review fallback for borderline cases

## Read-only by default
Integrations with recruiting systems default to read-only. Write capabilities require explicit additional authorization, separate API keys with write scope, and a written rationale documenting why direct write through automation is needed vs system UI.

## Idempotency for retry safety
Every webhook handler, API endpoint, and automation step must be idempotent. ATS systems often retry on timeouts; non-idempotent code produces duplicate candidates, duplicate applications, duplicate offers.

## Schema-driven, not string-driven
ATS APIs return structured data. Always parse to typed schemas, validate, then operate on structured data. Never regex-extract from raw API responses in production code.

## Test against staging recruiting systems
Production ATS contains real candidate data. All integration testing happens against staging Ashby/Greenhouse/Lever instances. Never test against production with real candidate data.

## Privacy and consent considerations
Candidate data handling must align with GDPR (EU candidates), CCPA (California candidates), and per-jurisdiction equivalents. Verify:
- Consent for data processing exists and is recorded
- Data retention policies are enforced (rejected candidate data has shorter retention than active candidates)
- Data subject access requests can be fulfilled

## Security review for new integrations
Any new integration with a recruiting system gets security review before production deployment. AI vendor integrations specifically require AI policy review per the firm's [AI policy](/en/learn/ai-policy-for-legal-teams/).

## Document the data flow
Each integration includes a data flow diagram showing: source system, data fields, transformation, destination system, retention policy. Lives in the repo `docs/` folder, updated when the integration changes.
```

3. **Commit the rules file.** Goes in version control with the rest of the project.
4. **Verify Cursor picks them up.** Cursor's Project Rules indicator should show the rules are active.

## What the rules do

When Cursor's AI is helping you write code in this project, the rules act as system-level instructions that shape the AI's suggestions:

- Suggests audit-log calls automatically when the AI sees you writing ATS API calls
- Refuses to suggest decision-making code without bias-safety considerations
- Flags non-idempotent webhook patterns
- Suggests schema validation when the AI sees raw-text parsing of structured ATS responses

The rules don't enforce behavior at runtime — they shape the AI assistant's suggestions during development.

## Where it fits

For recruiting teams that have a "recruiting engineer" role (or a recruiting-ops manager doing engineering work themselves), these rules ensure AI-assisted development produces code that matches recruiting-tech conventions and respects the bias-safety considerations specific to hiring code.

For recruiting teams without dedicated engineering capacity, this is less directly useful — but worth installing in any vendor- or partner-developed recruiting-tech project to encourage compatible conventions.

## Watch-outs

- **Rules require Cursor Project Rules support.** Older Cursor versions don't support project-scoped rules; verify before deploying.
- **Don't over-specify.** Rules that cover every possible style choice produce over-restrictive AI suggestions. Focus on the rules that prevent material bias, privacy, or candidate-data risk.
- **Update with practice.** The conventions evolve as the team's stack evolves. Review the rules quarterly; remove what's no longer relevant; add what's been learned.
- **Rules don't replace code review or bias audit.** They shape suggestions; human code review and explicit bias-audit infrastructure remain required.
