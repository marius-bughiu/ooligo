Un flow n8n qui orchestre la phase de collecte de l'[ediscovery](/fr/learn/ediscovery/) (le stade « Collection » de l'EDRM) — extrait les données de la liste des dépositaires depuis le SIRH du cabinet, génère des demandes de collecte par dépositaire contre les sources de données du cabinet (Google Workspace, Microsoft 365, Slack, partages de fichiers, SaaS personnalisé), suit la complétude de la collecte et la chaîne de conservation, et envoie les données collectées vers l'espace de travail [Relativity](/fr/tools/relativity/) (ou [Everlaw](/fr/tools/everlaw/) / [Logikcull](/fr/tools/logikcull/)) pour traitement. Chaque étape écrit dans un journal d'audit immuable que le conseil utilise pour défendre l'adéquation de la collecte. Remplace la collecte manuelle de l'administrateur legal-ops par tableur et captures d'écran par un flow déterministe.

## Quand l'utiliser

- Les cabinets avec des besoins réguliers en ediscovery — typiquement ceux ayant des portefeuilles contentieux actifs où la collecte se produit plusieurs fois par an.
- Le nombre de dépositaires par dossier est suffisamment important pour que la collecte manuelle soit opérationnellement infaisable (typiquement >5 dépositaires par dossier).
- Le cabinet dispose de capacités IT/ingénierie pour câbler la couche de connecteurs (Google Workspace Vault, M365 eDiscovery, Slack Discovery API, etc.). Le flow est l'orchestration ; les connecteurs sont par système.
- Le conseil valide le périmètre de collecte par dépositaire ; le flow exécute contre le périmètre approuvé.

## Quand NE PAS l'utiliser

- **Collectes à dépositaire unique** — le manuel convient ; le coût de configuration du flow (180 minutes plus câblage des connecteurs) ne se justifie pas.
- **Remplacer l'expertise en documentation de chaîne de conservation.** Le flow génère des enregistrements d'audit ; le responsable ediscovery valide que les enregistrements répondent aux exigences de chaîne de conservation de la juridiction. Les différentes juridictions ont des exigences différentes.
- **Définir automatiquement le périmètre de collecte.** Le conseil définit le périmètre selon le dossier ; le flow exécute contre le périmètre, il ne le rédige pas.
- **Premiers dossiers du cabinet** sans procédure de collecte établie. Le flow code une procédure ; s'il n'y a pas de procédure à coder, définissez-la d'abord.

## Configuration

1. **Importez le flow.** Déposez `apps/web/public/artifacts/evidence-collection-ediscovery-n8n/evidence-collection-ediscovery-n8n.json` dans votre instance n8n.
2. **Configurez les credentials.** Par source : Google Workspace (API Vault ; compte de service avec autorité déléguée), Microsoft 365 (API du Centre de conformité ; enregistrement d'application par tenant), Slack (API Discovery — disponible uniquement sur Enterprise Grid), SIRH (source des dépositaires). Plus Relativity / Everlaw / Logikcull (la plateforme e-discovery) et Postgres (journal d'audit).
3. **Rédigez le modèle de périmètre de collecte par source.** Par source de données, documentez : quels périmètres sont collectables (plage de dates, termes de recherche, filtres spécifiques au dépositaire), quelles sont les limites de débit par source, quel est le format de sortie attendu.
4. **Configurez le modèle de chaîne de conservation.** Par dossier et par dépositaire : qui a collecté (nom du compte de service + réviseur humain), quand, quoi a été collecté, hash de la collecte à l'achèvement. Modèle dans `_README.md`.
5. **Configurez l'intégration de la plateforme e-discovery.** API de traitement Relativity ou équivalent pour Everlaw / Logikcull. Le flow envoie vers un espace de travail par dossier ; le pipeline de traitement (déduplication, OCR, etc.) s'exécute dans la plateforme.
6. **Test à blanc sur un dossier clôturé.** Rejouez la collecte pour un dossier achevé le trimestre précédent. Confirmez que le volume collecté correspond à ce qui a été originellement produit et que les enregistrements de chaîne de conservation correspondent à ce que le conseil a certifié.

## Ce que le flow fait

Huit nœuds. Orchestration par dépositaire et par source, avec chaîne de conservation à chaque étape.

1. **Collection Request Trigger** — webhook depuis la plateforme legal-ops quand le conseil marque le périmètre de collecte comme approuvé.
2. **Load Custodian + Scope** — extrait la liste des dépositaires + le périmètre par dépositaire et par source depuis le plan de collecte du dossier.
3. **Per-Source Dispatch** — répartit une branche par source de données et par dépositaire. La partie la plus complexe du flow — chaque source a sa propre API et ses propres contraintes de limite de débit.
4. **Source : Google Workspace Vault** — dossier Vault créé (ou réutilisé), conservation émise, recherche exécutée contre Gmail / Drive / Agenda du dépositaire dans le périmètre, résultats exportés.
5. **Source : M365 Compliance** — recherche de contenu exécutée contre la boîte aux lettres / OneDrive / Teams du dépositaire dans le périmètre, résultats exportés via le Centre de conformité.
6. **Source : Slack Discovery** — API Slack Enterprise Grid Discovery ; export par dépositaire et par canal dans le périmètre.
7. **Hash + Chain-of-Custody Append** — chaque export par source est hashé (SHA-256), et un enregistrement de chaîne de conservation est ajouté à la table d'audit : `{matter_id, custodian_id, source, scope_summary, collected_at, collected_by_service_account, hash, file_count, byte_count}`.
8. **Upload to E-Discovery Platform** — envoi des exports vers l'espace de travail Relativity par dossier ; déclenchement du job de traitement ; enregistrement de l'ID de chargement côté plateforme dans le journal d'audit pour la traçabilité.

## Réalité des coûts

- **Coûts des connecteurs / plateformes sources** — Google Vault, M365 E5 avec Advanced eDiscovery, Slack Enterprise Grid ont tous des coûts par siège. Le flow ne les réduit pas ; il les rend utilisés efficacement.
- **Exécutions n8n** — de longue durée (les exports volumineux prennent des heures) ; utilisez le mode queue de n8n pour la production.
- **Coût de traitement de la plateforme e-discovery** — Relativity / Everlaw / Logikcull facturent tous au Go traité ; le flow ne change pas cette arithmétique.
- **Temps de l'administrateur legal-ops** — le gain. L'orchestration manuelle d'une collecte à 10 dépositaires sur 4 sources représente des jours de travail ; le flow s'exécute en heures sans surveillance.
- **Temps de configuration** — 180 minutes pour le flow lui-même + câblage significatif des connecteurs par source (les connecteurs constituent l'essentiel de la configuration réelle).

## Métriques de succès

- **Temps depuis l'approbation du conseil jusqu'à la collecte complète** — devrait passer de jours/semaines (manuel) à heures (flow), selon la durée des jobs d'export de la plateforme source.
- **Complétude de la chaîne de conservation** — devrait être à 100 % par dossier. Toute lacune est un risque de défendabilité.
- **Dérive de volume** — volume collecté par le flow vs périmètre attendu par le conseil. Dans les 10 % est normal (calibrage des filtres) ; >25 % déclenche une révision du périmètre.

## Alternatives

- **vs modules de collecte natifs de la plateforme e-discovery** ([Relativity](/fr/tools/relativity/) Collect, [Everlaw](/fr/tools/everlaw/) Collections). Choisissez ceux-ci si votre équipe vit dans la plateforme et que ses connecteurs couvrent vos sources. Le flow est pour les dossiers à source personnalisée ou les dossiers couvrant plus de sources qu'une seule plateforme ne couvre nativement.
- **vs outils commerciaux d'orchestration de collecte** (Reveal Brainspace, OpenText EnCase, Cellebrite, Onna). Choisissez ceux-ci pour les dossiers les plus complexes avec des exigences de niveau forensique. Le flow est le juste milieu léger pour l'ediscovery d'entreprise de routine.
- **vs collecte manuelle.** Viable à petite échelle ; ne scale pas sur les dossiers multi-dépositaires.

## Points de vigilance

- **Intégrité de la chaîne de conservation.** *Protection :* chaque export par source est hashé au moment de la collecte et à nouveau avant l'envoi vers la plateforme e-discovery. Les discordances de hash interrompent l'envoi et alertent le responsable ediscovery.
- **Dérive du périmètre sur la collecte automatisée.** *Protection :* le périmètre du flow est lu depuis le plan de collecte approuvé par le conseil ; élargir le périmètre en cours d'exécution nécessite un amendement du plan, pas une modification du flow. Le journal d'audit capture le SHA du plan par exécution.
- **Épuisement des limites de débit de la plateforme source.** *Protection :* des limiteurs de débit par source dans les nœuds par source du flow. L'API Slack Discovery a en particulier des limites de débit agressives — le flow module sa cadence en conséquence.
- **Exposition aux privilèges lors de la collecte.** *Protection :* la collecte capture tout dans le périmètre ; la révision des privilèges se fait en aval dans la plateforme e-discovery (le [skill de révision par lot des privilèges](/fr/workflows/privilege-review-batch-skill/) est l'étape suivante). Le flow NE pré-filtre PAS le contenu privilégié — c'est une décision aval.
- **Préoccupations de confidentialité des dépositaires.** *Protection :* le flow opère contre les systèmes que le dépositaire utilise pour le travail ; les comptes personnels (Gmail personnel, Slack personnel) sont hors périmètre à moins que le conseil ne les ait explicitement nommés. Le plan de collecte documente la limite.
- **Localisation des données inter-juridictions.** *Protection :* les données des dépositaires résidant dans l'UE peuvent être soumises aux considérations de localisation des données RGPD ; le périmètre par dépositaire du flow signale les dépositaires résidant dans l'UE pour une révision du traitement des données avant l'export vers un espace de travail e-discovery hors UE.
