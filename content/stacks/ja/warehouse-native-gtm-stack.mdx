適格アカウントの定義は、すでにウェアハウスの中にあります。このスタックの役割は、その定義の 2 つ目のコピーをマーケティングツールの中で維持させないことです。Snowflake または BigQuery がモデリング済みの顧客テーブルを保持し、[Hightouch](/ja/tools/hightouch/) がそれを外部へ同期し、[Clay](/ja/tools/clay/) がウェアハウス単体では生成できないフィールドを補い、[HubSpot](/ja/tools/hubspot/) で人間が結果に対して動きます。

この構成を選ぶ理由は、アーキテクチャの好みではありません。独自のセグメントビルダーを持つ GTM ツールは、いずれ「誰が顧客か」を巡って dbt と食い違い、その 2 つの定義を四半期ごとに突き合わせるコストが、アクティベーション層の年間費用を上回るからです。立ち上げには 6〜10 週間を見込んでください。その大半は 3 つのツールではなく、データモデルに費やされます。

## 各パーツの役割

- **ウェアハウスが信頼できる唯一の情報源です。** Snowflake、BigQuery、Databricks、Redshift のいずれでも構いません。ただし後述のバリエーションに 1 点だけ注意事項があります。dbt モデルは、GTM が実際に動く根拠となるフィールドを持つアカウント単位のテーブルを 1 つ生成します。ICP ティア、フィットスコア、プロダクト利用状況、オープンパイプラインのフラグなどです。下流では何もセグメントを定義しません。下流のツールは定義を読むだけです。この層こそがスタック全体を役員会で説明可能にするものであり、同時に誰も売ってくれない層でもあります。

- **[Hightouch](/ja/tools/hightouch/) はアクティベーションのバスです。** ウェアハウスに対して SQL を書き、同期を定義すると、行が HubSpot のフィールド、広告プラットフォームのオーディエンス、ライフサイクルツールのプロファイルとして着地します。顧客データの 2 つ目のコピーがベンダー側のストレージに残ることはありません。無料の Basic Reverse ETL ティアはアクティブな同期 2 本までに制限されますが、宛先数とユーザーシート数は無制限です。有料の Composable CDP ティアはシートではなく monthly tracked rows で課金されるため、同じデータ量なら 40 人のグロースチームでも 4 人のチームと同額になります。トライアル中に片付けるべきプロビジョニング上の注意点が 1 つあります。Hightouch のドキュメントは、自社製 MCP サーバーがすべてのワークスペースで有効になっているわけではなく、追加費用はかからないものの申請が必要だと明記しています。

- **[Clay](/ja/tools/clay/) は欠損を埋めます。** ウェアハウスが持つのは観測できたものだけです。Clay は観測できなかったものを供給します。ファーモグラフィック、従業員数の変動、テクノグラフィック、転職情報などです。Snowflake 連携には Insert Row、Lookup Row、Upsert Row のアクションが用意されているため、エンリッチメントの実行結果は誰も読まない Clay のテーブルで終わらず、ステージングテーブルへ書き戻せます。2026 年 8 月時点で、Clay の BigQuery 連携ページは依然として Coming Soon と表示されています。この非対称性が決めるのは配管であって、アーキテクチャではありません。

- **[HubSpot](/ja/tools/hubspot/) はアクション層であり、真実の層ではありません。** 担当者の割り当て、シーケンスへの登録、ディールステージ、タスク。このスタックを成立させる運用ルールはひとつです。Hightouch の同期が書き込む HubSpot プロパティは、手動編集を禁止します。営業担当者が CRM の画面で `icp_tier` を上書きできるなら、真実の源はふたたび 2 つになり、前提そのものが崩れます。これらのプロパティは初日にロックしてください。

### 名前のついた受け渡し

1. **モデルから CRM へ。** dbt が `gtm_accounts` をマテリアライズ → Hightouch の同期が読み取り → HubSpot の会社プロパティ (`icp_tier`、`fit_score`、`next_best_action`) が更新されます。tracked rows のメーターに課金されるのは変更された行だけであるべきで、それは Hightouch ではなくモデル側の性質です。
2. **欠損からエンリッチメントへ。** ファーモグラフィックが欠けたアカウントのウェアハウスビュー → Clay の Lookup Row またはテーブルインポート → エンリッチメント実行 → Clay の Upsert Row が `clay_enrichment_staging` へ書き込み → dbt がアカウントモデルにマージ → 次の Hightouch 同期が新しいフィールドを外部へ運びます。
3. **プロパティ変更から営業アクションへ。** `icp_tier` が Tier 1 に切り替わる → HubSpot のワークフローが担当者を割り当て、対応するシーケンスにコンタクトを登録します。この受け渡しは完全に HubSpot の中で完結し、Hightouch の責任は書き込みの時点で終わっています。
4. **結果をウェアハウスへ戻す。** ディールステージ、シーケンスの結果、closed-won のステータスをウェアハウスへ戻し、次回のモデル実行が推測ではなく結果に対してスコアリングできるようにします。後述のティア判断が最も効いてくるのが、この経路です。

## この組み合わせを選ぶ理由

わかりやすい代替案は、Hightouch を外して HubSpot 自身のウェアハウス同期を双方向で使うことです。その前に計算してください。HubSpot のドキュメントは、Snowflake 同期を Data Hub または Smart CRM の Enterprise レベルと HubSpot Credits の背後に置き、同期はスケジュール実行でリアルタイム更新ではないと明言し、ソースとなるテーブルまたはビューを 10 GB、200 カラム、1 回の実行あたり 3,000 万レコードに制限しています。Data Hub Enterprise の掲載価格は月額 $2,000 です。つまり自前案は年間 $24,000 かかり、スケジュール実行のみで、宛先はすでに持っている CRM 1 つだけです。

Vendr によれば、Hightouch の年間契約額の中央値は分析対象 170 件で $15,000、レンジは $9,600 から $75,000、定価からの平均割引率は 26% です。HubSpot のティア引き上げより安い金額で、CRM への経路に加えて 300 を超える連携カタログの広告・ライフサイクル・サポート宛先すべてが手に入ります。この比較で HubSpot が有利になるのは、CRM が本当に永続的に唯一の宛先である場合だけであり、そうであればこのスタック自体が不要です。

2 つ目の理由は、各層がちょうど 1 つの仕事しか担わないことです。ウェアハウスが定義し、Hightouch が運び、Clay が埋め、HubSpot が動きます。数字が合わないとき、確認すべき場所は 1 か所しかありません。境界を曖昧にしたスタック — モデリングもする CDP、エンリッチメントもする CRM — は、3 つのツールがわずかに異なる売上数値を保持し、どれが正しいか誰も言えないという失敗モードを生みます。

## コストの実態

シート数 10、データ量が中程度のミッドマーケット B2B チームの年間レンジです。

- **ウェアハウス (増分のみ)**: BigQuery は米国マルチリージョンのオンデマンドでスキャン 1 TiB あたり $6.25、Enterprise エディションでスロット時間あたり $0.06 を公開しています。Snowflake は価格ページに静的な定価を掲載しておらず (レートはプラットフォームとリージョンで変動します)、第三者のトラッカーは Standard を 1 クレジット $2.00〜$2.50、Enterprise を $3.00 前後としています。GTM アクティベーションは既存請求への増分として扱ってください。現実的には年間 $2K〜$12K で、行数よりも同期頻度に大きく左右されます。
- **Hightouch**: Vendr によると年間中央値 $15,000。同じ情報源は、monthly tracked rows が 100,000 までで月額 $1,000〜$2,500、100,000 から 100 万で月額 $2,500〜$8,000 というレンジを示しています。無料ティアより先は何も公開されていないため、ここの数値はすべてベンダーの見積もりではなく購入者側の報告です。
- **Clay**: Launch が月額 $185 (年払いで $167)、Growth が月額 $495 (年払いで $446) です。2026 年 3 月 11 日の価格改定で、課金は Data Credits と Actions の 2 つのメーターに分割されました。セルフサーブのチームは年間 $2,000〜$5,400 に落ち着きます。Enterprise 契約は年間 $30,000 前後が中央値として報告されています。
- **HubSpot**: Sales Hub Professional は年払いで 1 シート月額 $90 (月払いなら $100) なので、10 シートで年間 $10,800、加えて初回のみのオンボーディング費用 $1,500 がかかります。Enterprise は 1 シート月額 $150 です。

**合計: 10 シートでおよそ年間 $30K〜$60K**、最大の費目は Hightouch です。Data Hub Enterprise も購入するなら $24,000 を加算してください。ただし Hightouch を買うのであれば、たいていその必要はありません。

どの請求書にも現れないコストがあります。dbt モデルの構築と継続的な保守 (これが本当の参加費です)、業務上の必要ではなく習慣で設定された同期スケジュールに起因するウェアハウスのコンピュート、そしていずれかのメーターが尽きた時点でプラン単価を上回って課金される Clay のトップアップです。

## 適合ルール

**このスタックが向いているケース**

- モデリング済みのアカウントまたは顧客テーブルを持つウェアハウスがすでに本番稼働している。アクティベーションはデータを作りません。モデルより先に買うのは空のパイプに払うことです。
- dbt プロジェクトのオーナーがいて、1 年後もそのオーナーが続く。このスタックには名前のついた担当者が必要で、いなければ劣化します。
- アクティベーション先が 2 つ以上ある、または 12 か月以内にそうなる見込みがある。宛先が 1 つだけならアクティベーションのバスは正当化できません。
- dbt とベンダーの画面の両方に現在存在するセグメント定義を指し示せて、両者が最後に食い違った時点を言える。それがこのスタックの取り除く具体的な痛みです。

**このスタックが向いていないケース**

- ウェアハウスがない。イベントを自前で収集するパッケージ型 CDP を買ってください。アクティベーションより先に必要なのは取り込みと ID 解決です。
- HubSpot が唯一の宛先で、今後もそうである。HubSpot ネイティブの Snowflake 同期は遅くティアにも縛られますが、ベンダーも請求も 1 つで済みます。
- チームの誰も SQL を書かない。ウェアハウスネイティブのパターンはベンダー画面を SQL と交換するものであり、その交換は実行できる場合にのみ有利です。
- プロダクトマーケットフィット前で、どのシグナルがコンバージョンを予測するかをまだ学習中である。このスタックは良いアカウントの定義を運用に載せるもので、定義を発見するものではありません。

## よくあるバリエーション

- **Snowflake の代わりに BigQuery。** Clay の経路以外はすべてそのままです。BigQuery のネイティブコネクタはまだ提供されていないため、エンリッチメントは Hightouch の同期経由で Clay の HTTP API (Growth プラン以上) へ流し、Clay からの書き戻しも同じ経路を使ってください。ホップが 1 つ増えるだけで、データモデルは何も変わりません。コネクタが提供されたらネイティブアクションに戻します。
- **HubSpot の代わりに Salesforce。** 買い手の購買部門や既存の Salesforce 組織がそれを強いる場合の正しい入れ替えです。Hightouch の宛先カタログはどちらもカバーするのでアクティベーション層は影響を受けません。変わるのは、Salesforce 自身の data cloud 提案が同じ予算を奪い合う点であり、それが安くなることはありません。
- **Clay を外す。** ファーモグラフィックのエンリッチメントがすでにウェアハウスへ届いているなら — ZoomInfo や Clearbit のデータシェア、あるいはデータチームがすでに取り込んでいるベンダーフィードなど — ここでの Clay は冗長で、スタックの中で最も外しやすい費目です。アカウント単位の AI リサーチが一括フィードにできない仕事をしている場合にのみ残してください。
- **Hightouch の代わりに Fivetran Census。** Fivetran は 2025 年 5 月に Census を買収し、Fivetran Activations として統合しました。取り込みのためにすでに Fivetran を買っていて請求を 1 本にまとめたいなら、こちらを選びます。アクティベーションのほうが難しい問題であれば Hightouch を選んでください。宛先カタログと ID 解決の層が深いのはこちらです。

## このスタックが置き換えないもの

- dbt モデル。Hightouch は渡された定義を、300 の宛先へ忠実かつ高速に配信します。誤った定義は、あらゆる場所で誤ったまま届きます。
- 取り込み。データをウェアハウスへ入れるのは Fivetran、Airbyte、ネイティブコネクタです。このスタックはデータが着地した後から始まり、着地させることには何も寄与しません。
- 未着手の ID 解決。1 人の人物がプロダクト、請求、CRM に 3 回現れているなら、アクティベーションはその 3 件を同期します。
- デマンドエンジン。ペイド、コンテンツ、アウトバウンドがこのスタックのスコアリングとルーティングの対象となるアカウントを生みます。このスタックが処理するのは量であって、量を生み出しはしません。
- カンバセーションインテリジェンスと営業メソドロジー。シーケンスが発火してミーティングが設定された後について、このスタックは何も主張しません。その先は [Gong](/ja/tools/gong/) を参照してください。
