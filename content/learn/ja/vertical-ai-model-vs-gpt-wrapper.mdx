それ単体では重要ではありません。そもそも問いの向きが間違っています。ベンダーが自社モデルを訓練しているかどうかは、そのベンダーのコスト構造、レイテンシー、デプロイ可能な場所についての事実であって、出力が自社の基準を満たすかどうかの予測材料ではありません。「バーティカル AI モデル」とは、ベンダーがドメインデータで重みを変更したという意味です。「GPT ラッパー」とは、重みは変更せず、他社の API の周りにプロンプト、retrieval、ツール、そして製品を構築したという意味です。どちらの説明にも、機能する製品と機能しない製品の両方が含まれます。

これは品質の等級では**ありません**し、それ自体が優位性でもありません。自社の重みが精度を保証することはなく、API 呼び出しが精度を否定することもありません。購買上の問いはもっと狭いものです。このベンダーが持っていて、同じ API key を持つ競合が 1 四半期では再現できないものは何か。そしてその答えは、次のフロンティアモデルのリリースを生き延びるか。

## ベンダーが「自社モデル」と呼ぶ 4 つの別物

この言葉は、コストと防御可能性で段ごとに約 1000 倍の開きがあるはしごを覆っています。

1. **プロンプトとコンテキストの設計。** システムプロンプト、ツール定義、出力スキーマ、チャンキング戦略。これはラッパーであり、モデルと呼ぶのはマーケティングです。同時に、同じベースモデル上の 2 製品の間で観測される品質差の大半は、ここから生まれます。
2. **独自の retrieval と embeddings。** ベンダーが訓練するのは生成器ではなく検索層です。Harvey は Voyage AI と共同で `voyage-law-2-harvey` を構築しました。米国の法律テキスト 200 億トークン超でファインチューニングした embedding モデルで、既製の embeddings と比べて無関係な検索結果を 25% 削減したと報告されています。
3. **独自のタスクデータでのポストトレーニング。** ベースモデル上での教師ありファインチューニングまたは強化ファインチューニング。2026 年時点で、ops ソフトウェアの「専用設計モデル」のほぼすべては実際にはこれです。
4. **ゼロからの事前学習。** 新しいベースモデル。ops ソフトウェアでこれを行う企業はほぼ存在せず、唯一の有名な試みがその理由を示しています。

## BloombergGPT の教訓

Bloomberg は自社コーパスで 500 億パラメータの金融モデルを事前学習し、2023 年 3 月に公開しました。同規模のオープンモデル、すなわち GPT-NeoX、OPT、BLOOM を金融 NLP タスクで上回りました。その後、Bloomberg のデータに一切アクセスできない GPT-4 がこれを上回ります。GPT-4 のリリース後に行われた独立した評価では、FinQA のゼロショットで 68.79% 対 43%、ConvFinQA で 76% 対 43%、FIN3 の固有表現抽出で F1 が 83% 対 61% と報告されました。

一般化できる読み方は「ドメインモデルは負ける」ではありません。**ドメインデータで事前学習した中規模モデルは同じ階級には勝ち、次のフロンティアリリースには負ける**ということであり、フロンティアのリリースは事前学習の投資が回収されるより速く到着します。独自コーパスの規模を売り文句にするベンダーは、数か月ごとに争い直される陣地を説明しているだけです。

## Harvey は 3 年ではしごを一巡した

Harvey がもっとも明快な事例なのは、この議論のすべての立場を実際に取ってきたからです。

- **2023 年** — 公開 API 経由のファインチューニングと素の RAG では不十分と判断し、OpenAI と共同で判例法モデルをファインチューニング。ブラインドテストでは、弁護士の 97% がファインチューニング済みモデルを GPT-4 より選好しました。
- **2025 年 5 月** — Anthropic と Google のモデルを追加し、OpenAI への排他的依存を終了。Harvey が挙げた理由は買い手として読む価値があります。すべてで首位のモデルは存在しないためタスク単位でルーティングすること、プロバイダーの障害や容量制約が失敗ではなく再ルーティングになる冗長性、そして workspace ごとの管理者レベルでのモデル選択です。
- **2026 年 6 月 18 日** — 自社の法務モデルシリーズを発表。Baseten、Fireworks AI、Applied Compute、Trajectory Labs、Nvidia と構築したポストトレーニング済みのオープンソースモデルで、フロンティアモデルに近い性能と報告されています。共同創業者の Gabe Pereyra は目標を、製品全体でフロンティア級の能力を手頃な価格と強固なセキュリティ体制で提供することだと説明しました。

最後の項目は注意して読んでください。表明されている動機は**価格とデプロイ体制**であって、汎用モデルでは埋められない能力差ではありません。これがバーティカルモデル論の誠実な形であり、多くのベンダーが買い手に提示する論とは別物です。

## 決め手になる数字

Harvey が Fireworks と公開した Legal Agent Benchmark の結果です。100 タスクの抜粋に対し、全基準を満たすことを求める厳格な全項目合格基準で測定されています。

| 構成 | 全項目合格 | コスト |
|---|---|---|
| Claude Opus 4.7（クローズドなフロンティア基準） | 14/100 | $954 |
| GLM 5.1（オープンモデル単体） | 12/100 | $121 |
| Kimi K2.6 + 教師ありファインチューニング | 15/100 | $84 |
| GLM 5.1 を worker、Opus 4.7 を advisor とする構成 | 18/100 | $368 |

より緩い平均スコア指標では 4 構成はほぼ収束します。GLM 5.1 が 0.8921、GPT-5.5 が 0.892、Opus 4.7 が 0.911 です。この表から 3 点が読み取れます。ドメインのポストトレーニングは、平均スコアをほぼ維持したまま約 8 倍のコスト削減を買いました。ハイブリッド構成は全項目合格でフロンティアモデルを上回り、そのコストは約 39% でした。そしてどの構成も 100 タスク中 20 タスクを超えて完遂できておらず、この領域が解決には程遠いこと、そして平均スコア中心のマーケティングがそれを覆い隠していることを示しています。

## ベンダーが持っていて複製できないもの

評価では、重みよりこちらを上位に置いてください。

- **データの権利。** Gong の立場は、契約上の権利を持つ数百億件の営業インタラクションに支えられており、訓練済みトラッカーで既製システムの 3 倍の精度を主張しています。[Eightfold](/ja/tools/eightfold/) は 16 億件のキャリアプロファイルと 160 万のスキル推定に支えられています。どちらも API key では再現できません。
- **評価基盤。** Harvey は Snorkel AI と BigLaw Bench および Legal Agent Benchmark を構築し公開しました。モデル変更が改善につながったとなぜ言えるのかを説明できないベンダーは、印象を売っています。
- **ワークフロー、権限、監査面。** 管理者が日々使う部分であり、モデルのリリースでは無効化されません。

## ベンダーへの診断質問

1. **この機能を今日動かしているモデルはどれで、6 か月前はどれでしたか。** 答えられないなら、バージョンドリフトは制御されておらず、精度のベースラインは再現できません。
2. **自社モデルが、御社がアクセスできるフロンティアモデルを上回るタスクを見せてください。そのうえで当社の文書で再実行させてください。** ベンダーのデータ上のベンダーのベンチマークは出発点であって証拠ではありません。
3. **当社のデータは訓練セットに入りますか。ゼロリテンションの選択肢は何ですか。** 「独自データセット」が自社の入力を指している場合があります。
4. **プロバイダーがモデルを廃止したらどうなりますか。** Harvey のマルチモデル方針は障害と容量制約を明示しています。単一プロバイダーのベンダーは、そのリスクを顧客の代わりに負っています。
5. **当社の量で、完了 1 タスクあたりのコストはいくらですか。** 上の表がその理由です。同じ出力でもアーキテクチャによって価格は 11 倍の幅があります。
6. **全項目合格ですか、平均スコアですか。** 基準単位の数字を求めてください。平均スコアは部分点が隠れる場所です。

## 注意点と、それぞれの対策

**システムプロンプトにすぎない「専用設計モデル」。** この主張はコストゼロで作れます。*対策:* 上のはしごのどの段に当たるのか、プロンプト、embeddings、ポストトレーニング、事前学習のいずれかを書面で確認し、その回答を契約の製品記述に入れてください。

**動くベースの上で凍結したファインチューン。** 2024 年のベースにポストトレーニングしたモデルは、フロンティアのリリースごとに相対的に劣化します。*対策:* 再訓練の頻度と現行チェックポイントの日付を確認し、更新時の判断項目にしてください。

**ロックインの手段として使われる自社モデル主張。** 出力が相手のモデルの中にしか存在しないなら、移行コストこそが製品です。*対策:* 出力と根拠資料を、自社で再取り込みできる形式で一括エクスポートできることを要求してください。

**コーパスそのものではなくコーパスの物語を買う。** ベンダーはデータセットの規模を挙げますが、それを訓練に使う権利があるかは述べません。*対策:* 行数ではなく、データ権利の根拠を求めてください。

**グラウンディングと訓練の混同。** 法務や GTM の精度問題の大半は、重みの問題ではなく retrieval の失敗です。*対策:* 「自社モデルを訓練しました」を精度への回答として受け入れる前に、[リーガル AI のグラウンディングとハルシネーション](/ja/learn/legal-ai-grounding-vs-hallucination/) と [RAG](/ja/learn/retrieval-augmented-generation-rag/) を確認してください。

## 実際に重要になる場面

API では満たせないデプロイ要件があるときには重要です。プロバイダーが対応していない法域でのデータ所在地、エアギャップ環境やソブリン環境への導入、リアルタイム機能のレイテンシー下限、あるいは単価の 8 倍差が予算項目になるほどの処理量です。こうした場合、自社の重みを制御するベンダーにはラッパーにはない選択肢があり、明示的に要求すべきです。

一方、契約レビューや conversation intelligence の製品を選ぶ 40 人規模のチームには重要ではありません。直近 20 件の文書または通話でツールを実行し、自社チームが作ったであろう成果物と照らして採点し、それを根拠に購入してください。重みはベンダーの技術課題です。エージェントと機能の寄せ集めを見分ける、より広いパターンについては [ops における AI エージェントとは何か](/ja/learn/ai-agent-for-ops/) を参照してください。
