Un prompt pack (aussi appelé bibliothèque de prompts ou collection de prompts) est un ensemble curé d'instructions textuelles sauvegardées que vous collez dans Claude pour diriger une tâche spécifique. Un Claude skill est un module d'instructions conditionné que Claude charge automatiquement, qui persiste entre les sessions et peut invoquer des fichiers de référence, des scripts et des workflows structurés sans que vous n'ayez à ressaisir quoi que ce soit. Le choix entre les deux est une question de construction ou de copie&nbsp;: si le travail est une tâche ponctuelle ou peu fréquente, un prompt pack est la bonne réponse et un skill relève de la sur-ingénierie. Si le travail est une tâche opérationnelle récurrente et à fort enjeu où la cohérence et la distribution au sein de l'équipe comptent, un skill est l'unité adaptée.

## Ce que ce n'est PAS

Un prompt pack n'est pas un skill. Un prompt est *réactif* — vous le fournissez à chaque session&nbsp;; Claude l'applique à ce que vous avez dit jusqu'alors et il disparaît ensuite. Un prompt pack organisé dans [Notion](/fr/tools/notion/), un Google Doc ou un dossier de fichiers `.txt` ne persiste pas automatiquement dans le contexte de Claude. Il ne charge pas de fichiers de référence. Il ne peut pas déclencher de sous-étapes sans que vous les orchestriez manuellement.

Un Claude skill n'est pas un prompt, même si son fichier SKILL.md contient des instructions en langage naturel. La différence réside dans la couche d'empaquetage et de persistance&nbsp;: un skill est enregistré dans Claude Code (ou partagé via un plugin), de sorte que Claude le découvre dynamiquement, le charge quand il est pertinent, et votre équipe peut l'invoquer par son nom sans toucher au fichier sous-jacent. Un skill peut également regrouper des ressources de référence — templates de clauses, rubriques de scoring, fiches persona — qui se chargent en même temps que les instructions.

## Ce qu'un prompt pack fait bien

Un prompt pack couvre la majorité de l'utilisation quotidienne de Claude, et c'est ainsi que cela devrait être. Les cas d'utilisation où un prompt pack est le bon choix&nbsp;:

- **Analyse ad-hoc.** Vous explorez un jeu de données, résumez une transcription de réunion ou rédigez une communication ponctuelle. Vous avez besoin que Claude applique un cadrage spécifique cette fois-ci&nbsp;; vous ne savez pas si vous en aurez besoin à nouveau.
- **Tâches peu fréquentes.** Vous faites une analyse concurrentielle trimestrielle&nbsp;? Un prompt bien rédigé collé depuis Notion prend 10 secondes et n'a aucun coût de maintenance.
- **Expérimentation de nouveaux workflows.** Avant de vous engager à conditionner un skill, un prompt pack vous permet d'itérer sur l'ensemble d'instructions sans toucher aux fichiers de configuration. Utilisez un prompt pack pour trouver la bonne méthode&nbsp;; convertissez en skill une fois la méthode stabilisée.
- **Utilisation individuelle.** Si le prompt est destiné au workflow d'une seule personne et ne sera pas partagé, un prompt pack dans un outil de notes personnel convient.

Le bon pattern pour un prompt pack&nbsp;: rédiger le prompt soigneusement, le stocker avec un nom clair et une note de contexte, et le récupérer quand nécessaire.

## Ce qu'un Claude skill fait qu'un prompt pack ne peut pas faire

Un skill possède quatre capacités qu'un prompt pack n'a pas&nbsp;:

1. **Persistance sans coller.** Un skill enregistré est toujours disponible dans le contexte de Claude sans que vous ayez à copier quoi que ce soit. Claude détecte qu'un skill est pertinent et le charge. Pour les workflows quotidiens, cela s'accumule&nbsp;: une équipe exécutant 15 analyses récurrentes cesse de copier 15 prompts différents.
2. **Ressources de référence incluses.** Un prompt peut dire à Claude «&nbsp;applique nos positions de repli standard pour les NDA.&nbsp;» Un skill *contient* réellement ces positions de repli comme fichier de référence que Claude lit pendant l'exécution. Le skill garantit que Claude utilise la version actuelle de ce document, pas ce que l'utilisateur avait copié le mois dernier.
3. **Distribution dans l'équipe et contrôle de version.** Un skill vit dans le référentiel ou est partagé via un plugin avec une version définie. Quand vous mettez à jour l'ensemble d'instructions, chaque membre de l'équipe qui exécute le skill reçoit la mise à jour. Une mise à jour de prompt pack demande à tout le monde de recopier le nouveau texte.
4. **Exécution de procédures séquentielles.** Un skill peut définir des méthodes à plusieurs étapes avec une logique de stage explicite — par exemple&nbsp;: lire le contrat, identifier les clauses à risque, scorer chacune selon une rubrique, retourner une sortie JSON structurée. Exécuter la même procédure depuis un prompt demande à l'utilisateur d'orchestrer manuellement chaque étape au fil des tours.

## Le déclencheur de conversion&nbsp;: quand passer du prompt pack au skill

Passez d'un prompt pack à un skill quand trois conditions sont réunies&nbsp;:

1. **La tâche se répète au moins chaque semaine, pour vous ou votre équipe.** En dessous de la fréquence hebdomadaire, le coût de maintenance d'un skill (le mettre à jour quand la méthode change) ne vaut pas l'investissement.
2. **Des erreurs de cohérence sont apparues.** La même tâche produit des sorties différentes selon les utilisateurs ou les sessions parce que chacun a une version légèrement différente du prompt, ou oublie une étape. Un skill élimine la divergence par copier-coller.
3. **La méthode est stable.** Vous avez exécuté la tâche suffisamment de fois pour savoir à quoi ressemble une bonne sortie, quels modes d'échec protéger et quels matériaux de référence elle nécessite. Convertir trop tôt un prompt expérimental en skill signifie que le skill devient une cible mouvante.

Un test pratique&nbsp;: si vous avez copié-collé le même prompt plus de 20 fois et commencé à maintenir des copies «&nbsp;version 2&nbsp;» et «&nbsp;version 3&nbsp;», vous gérez déjà un mauvais skill. Formalisez-le.

## Comparaison des coûts et de la maintenance

| Dimension | Prompt pack | Claude Skill |
|---|---|---|
| Temps de mise en place | Minutes | 1–4 heures (rédiger SKILL.md + fichiers de référence + tests) |
| Friction par utilisation | Coller le prompt à chaque session | Zéro — Claude le charge automatiquement |
| Distribution dans l'équipe | Chacun maintient sa propre copie | Source unique&nbsp;; mettre à jour une fois |
| Ressources de référence | L'utilisateur doit les coller ou s'en souvenir | Incluses&nbsp;; toujours à jour |
| Versionnage de la méthode | Ad-hoc (v1, v2, final, FINAL) | Suivi sous Git |
| Coût en tokens | Tokens complets du prompt à chaque session | 30–50 tokens au repos&nbsp;; ~5&nbsp;000 à l'activation |

L'investissement de mise en place d'un skill se rentabilise quand la tâche tourne plus de ~20–30 fois. En dessous de ce seuil, le prompt pack est plus rapide quelle que soit la mesure.

## Pièges courants

- **Construire un skill trop tôt.** Si vous ne savez pas encore à quoi ressemble une bonne sortie, conditionner le prompt en skill signifie que vous éditerez SKILL.md chaque semaine plutôt que de simplement mettre à jour un fichier texte. Attendez que la méthode se stabilise.
- **Maintenir un prompt pack au-delà de sa durée de vie utile.** Quand vous avez 40 prompts dans une base Notion et trois personnes dans votre équipe utilisant des versions différentes du même prompt, vous portez le surcoût d'un skill sans aucun de ses avantages. Convertissez les plus fréquents.
- **Traiter la rédaction d'un skill comme un exercice d'écriture.** La section centrale d'un SKILL.md est le bloc «&nbsp;quand ne pas invoquer&nbsp;» et la spécification du format de sortie, pas la description introductive. Un skill qui ne spécifie pas précisément le format de sortie génèrera des sorties incohérentes quelles que soient la qualité des instructions.
